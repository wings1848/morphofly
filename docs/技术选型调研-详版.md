## 0. 一句话结论（先看这个）

**桌面端用 Tauri 2.x（Rust）做壳 + 音频全部走原生（cpal/rodio）+ UI 用 Web 做粒子。**
**ESP32 端不要指望 Go/Rust，用 C/C++（ESP-IDF + esp-sr + LVGL），只共享协议层。**

理由三句话：
1. Tauri 二进制最小（官方 <600KB，实测社区 3MB 级），且 iOS/Android 是官方支持（2024-10 起 stable）。
2. **音频千万别走 WebView 的 `getUserMedia`** —— 三个平台三套坑，Linux 上几乎是雷区。
3. ESP32-S3 上 TinyGo 只有 416KB DRAM、堆上限 ~298KB、还不支持 PSRAM；跑唤醒词+显示+WebSocket 不可能。

### 1.3 各框架的「坑」清单（重点看这段）

**Wails**
- **Linux 门槛最高**：v3 默认要求 **GTK4 + WebKitGTK 6.0**（Ubuntu 24.04+/Debian 13+/Fedora 40+）。Ubuntu 22.04 / Debian 12 / RHEL 9 只能用 `-tags gtk3` 的 legacy 构建，**v3.1 就删掉**。只有 WebKit2GTK 4.0 的发行版直接不支持。
- **v3 还是 beta**：官方 FAQ 原话「Wails v3 is beta software with a stable desktop API」。从 2024-12 的 alpha.8 走到 2026-10 的 beta.34，快两年了还没 3.0.0。
- **移动端明确是 experimental**：官方 roadmap 原文「Android and iOS support is experimental and does not block the desktop Beta」。
- **音频**：v3 新加了跨平台 `Permissions` map（`PermissionMicrophone`），Linux/Windows/macOS 12+ 都能授权。但 v2 时代 Linux 上 `navigator.mediaDevices` 直接是 `undefined`（discussion #2697），社区结论是「WebView 不该碰硬件，应该在 Go 后端做」。

**Tauri**
- **Linux 的 `getUserMedia` 需要自己动手**：WebKitGTK 的 `enable-media-stream` **默认关闭**，且默认 `permission-request` handler **拒绝一切请求**。真实案例：unsloth 的 Tauri 桌面版在 Ubuntu 上麦克风完全用不了（issue #8678）。需要拿到 `webkit2gtk::WebView` 手动开 + 挂权限回调。
- **macOS 双保险**：`NSMicrophoneUsageDescription`（Info.plist）+ **Hardened Runtime 的 microphone entitlement**。少了 entitlement，`hardenedRuntime` 默认 true 会直接挡掉硬件访问。
- **Android 双层权限**：系统弹窗 + WebView 的 `WebChromeClient.onPermissionRequest` 是**两层独立**的。只加 `RECORD_AUDIO` 不够，还要 `MODIFY_AUDIO_SETTINGS`（否则 `NotReadableError`）、`AudioManager.MODE_IN_COMMUNICATION`、以及 `mediaPlaybackRequiresUserGesture=false`。官方 discussion #12732 有完整 Kotlin 代码。
- **iOS**：`navigator.mediaDevices` 从 iOS 14.3 才有，之前完全不可用；且 iOS 15 起 WKWebView 麦克风**切后台会被静音**（Apple 论坛 thread 689182）。另有已知 bug：`AnalyserNode.getByteFrequencyData()` 对 `getUserMedia` 流返回全 0（影响 iOS 18 及以前）——**这会直接打掉你的音频可视化**。
- **Windows 7 已放弃**（2.12 起），MSRV 提到 1.90。

**egui / iced / slint / fyne / gio**
- 全都没有音频，必须外挂原生库。
- iced 官方 FAQ 直说「Not really. Iced is not designed for mobile.」
- Slint 的许可证对嵌入式要钱（见 §1.5）。
- Fyne 无 GPU 加速，粒子特效会卡；Gio 有 GPU 但生态小（主仓 star 仅 2.2k）。

### 1.4 关于「内存占用」的诚实说明

所有「Wails 10MB 内存」「Tauri 80MB 内存」的说法都**不可直接采信**：

- Wails 官方说「~10MB baseline memory」，但它同时说二进制 10–15MB。一个带 WebView 的进程只占 10MB RAM 在技术上不成立（WebView 渲染进程本身就要几十 MB）。
- 真正可比的是第三方 benchmark：Wails 空应用 Linux x64 release **≈53MB RAM**，Electron ≈77MB（dev.to，2026-10-08）。
- Tauri 的 WebView2（Windows）会额外起 `msedgewebview2.exe` 子进程，任务管理器里看是两个进程。
- **【未查证】** 没有任何一方给出「同一台机器、同一测量方法、同一时刻」的三框架对比数据。**建议你自己跑一次再定。**

### 2.2 Wails / Tauri 里到底该用 WebAudio 还是原生？

**结论：用原生。别用 WebView 的 `getUserMedia`。**

理由按重要性排：

1. **回声消除拿不到参考信号**。AEC 的本质是「我知道我正在播什么，从麦克风里把它减掉」。如果播放走 WebView、采集走原生（或反过来），参考信号就断链了，AEC 直接失效。你要做**可打断的全双工**，这条是致命的。
2. **Linux 上根本跑不起来**（WebKitGTK 默认关 media-stream + 默认拒权限）。你要为它写平台特定代码，还不如一开始就走原生。
3. **iOS 的 `AnalyserNode` 有 bug**（对 `getUserMedia` 流返回全 0）——你的「音频可视化」直接没了。
4. **延迟不可控**。WebView 里的音频要过 Chromium/WebKit 的音频服务层，`latencyHint` 只是「建议」。原生 cpal/malgo 能拿到真实 buffer size。
5. **权限模型不统一**。三平台三套，还要处理「开发模式 vs 打包后」的差异（Wails issue #4270 就是这个：`wails3 dev` 弹不出麦克风权限，直接跑二进制才行）。

**推荐做法（Tauri 为例）**：
```
cpal 采集 16kHz mono i16
  → webrtc-audio-processing（AEC，用「正在播放的 TTS 音频」当 reference）
  → VAD / 唤醒词（rustpotter 或 openWakeWord 的 Rust 移植）
  → WebSocket 发云端
  ← WebSocket 收 PCM
  → 一路给 rodio 播放
  → 一路喂回 AEC 当 reference
  → 每 16ms 算一次 FFT，把 64 个 float 通过 IPC Channel 推给 WebView 画粒子
```
WebView 只干一件事：**收 64 个 float，画球和粒子**。它永远不碰麦克风。

**IPC 带宽够不够？** 64 bin × 4 byte × 60fps = **15KB/s**。Wails v3 的 Streams 官方实测 Go→JS 峰值：macOS 3117MB/s、Linux 226MB/s、Windows 100MB/s，p99 延迟 1–2ms。Tauri 的 `ipc::Channel` 同级。**完全不是瓶颈。**

### 2.3 AEC（回声消除）怎么做

| 方案 | 可用性 | 说明 |
|---|---|---|
| **浏览器/WebView 的 `echoCancellation: true`** | ⚠️ 能复用，但**不建议依赖** | Chromium 里确实走 WebRTC AEC3；WKWebView 会创建 `VoiceProcessingIO` AudioUnit（副作用：会把**同一台 Mac 上其他进程**的麦克风输入压低约 29dB）。但你在 WebView 里没法控制 AEC 的参考信号，也没法在原生侧复用。 |
| **webrtc-audio-processing（Rust）** | ✅ **桌面端首选** | AEC3 + NS + AGC + VAD 全套，10ms 帧粒度，`bundled` feature 自带 C++ 源码。代价：编译要 clang/meson/ninja，二进制 +2–5MB（未实测）。 |
| **SpeexDSP AEC** | ✅ 轻量备选 | 算法老、CPU 低，但抗抖动差（约 ±50ms 以内），双讲处理弱于 AEC3。适合 ESP32 或极低配。 |
| **Go 侧 WebRTC APM** | ⚠️ 只有社区 cgo 包 | 如 `voicedaemon` 里的 `capm` 包（`CreateWithAEC` → AEC3）。**没有官方 Go 绑定**，等于自己维护一份 cgo 封装。 |
| **macOS `VoiceProcessingIO`** | ✅ 系统级，质量最好 | `AVAudioEngine.setVoiceProcessingEnabled(true)` 一行开启，和 FaceTime/Siri 同一套。但只能在原生侧用，且会污染其他进程的输入。 |
| **ESP32 `esp-sr` AFE** | ✅ 端上最强 | 自带 AEC（SR/VOIP/FD 多种模式），输入格式 `"MR"`＝1 麦克风 + 1 播放参考。资源占用见 §3。 |

### 2.4 全双工（同时播放+采集）要注意什么

1. **同一个设备、同一个采样率、同一个时钟**。别一边 48k 一边 16k 让系统重采样，会引入未知延迟，AEC 的延迟估计会崩。
2. **Linux 上别用 ALSA 直连**。ALSA 是独占的，同时开 input/output 容易 `Device or resource busy`。走 PulseAudio / PipeWire（cpal 有对应 feature）。
3. **播放要环形缓冲，采集要定长帧**。播放侧写 ring buffer（建议 200–500ms 余量抗抖动），采集侧固定 10ms 或 20ms 一帧喂 AEC。
4. **打断（barge-in）三连**：VAD 检测到人声 → **立刻**停播放并清空 ring buffer → 发 `cancel` 给云端。顺序不能错，否则用户会听到自己的回声。
5. **AEC 的 reference 必须是「真正送到扬声器的那一路」**，不是「你打算送的那一路」。中间有音量调节、有重采样，reference 都要跟着变。
6. **macOS 上如果开了 `VoiceProcessingIO`，它会改设备的采样率/通道数**，你的 cpal 配置要能容忍。
7. **Windows 上 WASAPI 共享模式有系统混音延迟**，要低延迟得走 exclusive mode（cpal 支持，但会独占设备）。

## 3. ESP32 可行性结论

### 3.1 一句话

**Go 和 Rust 在 ESP32-S3 上都能跑「音频 I/O」，但都跑不动「唤醒词 + 显示 + 实时语音」这一整套。ESP32 端请用 C/C++。**

### 3.2 Go / TinyGo 在 ESP32 上：不行

| 指标 | 实测/官方数据 | 结论 |
|---|---|---|
| 可用 DRAM | **425,984 字节（416KB）**，其中堆上限 **298,287 字节** | 这是 TinyGo 在 ESP32-S3 上的真实数字（Zenn 实测，2026-10） |
| PSRAM | **TinyGo 0.42/0.43 的 ESP32-S3 链接脚本只处理内部 SRAM 的 416KB，完全不支持 PSRAM**（PR #5554 未合） | 8MB PSRAM 用不上 |
| GC | **保守式 GC**（把长得像指针的值都当指针），堆满才回收 | 实时音频会因 GC 停顿爆音 |
| goroutine 栈 | **固定大小，不增长**，ESP32-S3 默认 8KB（`-stack-size`） | 稍复杂的 JSON 解析就栈溢出 |
| I2S | **TinyGo 0.43.0（2026-10-09）刚加上 ESP32 I2S 支持**（PR #5787） | 能做，但很新 |
| 显示 | 有 ST7789/ILI9341 驱动（tinygo-org/drivers） | 能做 |
| 唤醒词 | **无任何 Go 版唤醒词引擎** | 死路 |
| WiFi | 0.41 起支持 ESP32-S3 的 espradio | 能用 |

**结论**：TinyGo 跑个「I2S 出声 + 点灯 + 连 WiFi 发数据」可以。跑唤醒词不行——WakeNet 是乐鑫的闭源 C 库（静态库 + 模型文件），没有 Go 绑定，TinyGo 也不支持链接这种二进制 blob 到 Xtensa 目标。

### 3.3 Rust 在 ESP32 上：能做，但绕不开 C

| 项目 | 版本(日期) | 定位 |
|---|---|---|
| `esp-idf-svc` | 0.53.0 (2026-09-15) | std 环境，绑定 ESP-IDF（含 FreeRTOS、WiFi、I2S 驱动） |
| `esp-idf-hal` | 0.47.0 (2026-09-15) | ESP-IDF 的 HAL 封装，含 I2S（std/PDM 都支持） |
| `esp-hal` | 1.2.2 (2026-09-18) | **no_std** 纯 Rust HAL，不依赖 ESP-IDF |

**能做的**：I2S 采集/播放、ES8311/ES7210 codec 驱动（社区有 `rusty_esp_audio` 等项目）、WebSocket（`esp-idf-svc` 带 TLS）。
**不能做的**：**esp-sr（WakeNet / AFE / MultiNet）是乐鑫的 C 静态库**，没有官方 Rust 绑定。你要么自己写 `bindgen` 封装，要么在 `esp-idf-svc` 项目里混编 C 组件。

**混编的代价**：那还不如直接用 C——你已经要为 esp-sr 写 C 胶水了，Rust 只覆盖剩下 30% 的代码，收益很小。

### 3.4 ESP32-S3 音频方案（现实做法）

**硬件组合**（市面主流）：
- **ESP32-S3-WROOM-1**（8MB Octal PSRAM + 16MB Flash）
- **ES8311**（单声道 codec：ADC + DAC + 耳放）— I2S 走数据，I2C 走控制
- **ES7210**（4 通道 ADC，做麦克风阵列）— 双麦/四麦
- 功放 NS4150，喇叭
- 屏幕：SPI 接口，240×240 圆屏（GC9A01）或 320×240（ESP32-S3-BOX-3）

**软件栈**：
```
ESP-IDF v5.x
├── esp_driver_i2s        （I2S std 模式，全双工）
├── esp_codec_dev         （ES8311/ES7210 驱动，v1.3.5）
├── esp-sr (AFE)          （AEC + NS + VAD + WakeNet）
├── LVGL v9 + esp_lvgl_adapter
├── esp_websocket_client  （或 esp_http_client 的 WS）
└── micro-opus / esp_llm_* （可选，Opus 编码省带宽）
```

**资源实测（乐鑫官方 benchmark，ESP32-S3）**：

| 配置 | 内部 RAM | PSRAM | 喂数据 CPU | 取结果 CPU |
|---|---|---|---|---|
| MR, SR, LOW_COST（AEC+VAD+WakeNet9） | **60.1 KB** | **739.7 KB** | 8.8% | 9.8% |
| MR, VC, HIGH_PERF（AEC+NS+VAD） | 91.1 KB | 822.2 KB | 32.2% | 4.7% |
| MMNR, SR, HIGH_PERF（双麦+参考） | 68.1 KB | 1200.4 KB | 24.9% | 22.9% |

WakeNet 单模型：**WakeNet9 @ 2ch = 16KB RAM + 324KB PSRAM，每 32ms 帧跑 3.0ms**；WakeNet8 @ 2ch = 50KB + 1640KB，10ms/帧。

> 注意：这些 PSRAM 数字意味着 **8MB PSRAM 是硬需求**，没有 PSRAM 的 ESP32-S3（如 N8R2 只有 2MB）跑不动双麦 AFE。

**显示性能（关键约束）**：Seeed 的 XIAO ESP32-S3 + 240×240 圆屏实测，SVG 动画从 **9 FPS 优化到 30 FPS** 需要五轮调优（Octal PSRAM、SIMD、双缓冲、SWAR）。**30 FPS 是 SPI 总线的物理上限**。

→ **你的「梦幻粒子」在 ESP32 上最多做到 240×240 @ 25–30fps，且必须用 LVGL 的 canvas 逐像素画，不能指望 GPU。**

### 3.5 最终建议

**ESP32 端：C/C++ 单独实现，只共享协议层。**

具体分工：
- **共享**：WebSocket 消息格式（JSON 控制帧 + 二进制 PCM 帧）、会话状态机定义、错误码、鉴权流程。
- **不共享**：音频 I/O、唤醒词、UI 渲染、网络重连策略（ESP32 的 WiFi 重连逻辑和桌面完全不同）。

如果一定要在 ESP32 上用 Rust，唯一合理场景是：**用 Slint**（它是唯一官方支持 ESP32-S3 的 Rust GUI，有 ESP-IDF 组件 `slint/slint v1.18.1`），但**嵌入式商用要买 Slint 商业许可**。

## 4. 推荐架构

### 4.1 分层图（文字版）

```
┌──────────────────────────────────────────────────────────────────┐
│  L5  UI 渲染层（每端独立实现，唯一允许用 Web 技术的地方）              │
│  ┌────────────┬────────────┬────────────┬────────────┬─────────┐ │
│  │ Desktop    │ Web        │ Android    │ iOS        │ ESP32   │ │
│  │ WebView    │ 浏览器      │ WebView    │ WKWebView  │ LVGL    │ │
│  │ Canvas/    │ Canvas/    │ Canvas/    │ Canvas/    │ canvas  │ │
│  │ WebGL      │ WebGL      │ WebGL      │ WebGL      │ 逐像素   │ │
│  └────────────┴────────────┴────────────┴────────────┴─────────┘ │
│          ↑ 只收「64 个 float 的频谱 + 状态枚举」，永不碰麦克风         │
├──────────────────────────────────────────────────────────────────┤
│  L4  IPC 桥（每端一套薄适配）                                       │
│  Desktop: Tauri ipc::Channel / Wails Streams                      │
│  Web:     WebSocket                                               │
│  Mobile:  Tauri 原生插件（Kotlin/Swift）                           │
│  ESP32:   直接函数调用（同进程）                                     │
├──────────────────────────────────────────────────────────────────┤
│  L3  音频管道（★ 每端必须原生实现，不可共享）                         │
│  采集 → AEC → VAD/唤醒 → 编码 ─┐                                   │
│  播放 ← 解码 ←───────────────┴→ AEC reference                     │
│  Desktop: cpal + webrtc-audio-processing + rodio                  │
│  Mobile:  AVAudioEngine(VPIO) / AAudio                            │
│  ESP32:   esp-sr AFE + esp_codec_dev                              │
├──────────────────────────────────────────────────────────────────┤
│  L2  会话核心（★★ 可共享，这是「一套代码」的真正价值所在）             │
│  · 状态机：Idle → Wake → Listening → Thinking → Speaking → Idle   │
│  · 打断逻辑：barge-in 判定、cancel 时序                             │
│  · 协议编解码：WS 帧格式、PCM 分片、重连退避                          │
│  · 工具调用 / 提示词 / 会话上下文                                     │
│  实现语言：Rust crate（推荐）或 Go package                          │
├──────────────────────────────────────────────────────────────────┤
│  L1  传输层（可共享协议定义，不可共享实现）                            │
│  Desktop/Mobile: tokio-tungstenite / gorilla-websocket            │
│  ESP32:          esp_websocket_client（C）                        │
│  Web:            浏览器原生 WebSocket                              │
└──────────────────────────────────────────────────────────────────┘
```

### 4.2 哪些能共享、哪些不能

| 层 | 能否共享 | 怎么做 |
|---|---|---|
| **L2 会话核心** | ✅ **必须共享** | 写成独立 Rust crate（`xiaodie-core`），无平台依赖，`no_std` 兼容更好 |
| **L1 协议定义** | ✅ 共享「定义」 | protobuf/JSON schema 放一个仓，各端生成代码 |
| **L5 UI** | ✅ 桌面+移动+Web 共享；ESP32 重写 | 前端代码一份，ESP32 用 LVGL 重画（同一套设计 token） |
| **L3 音频** | ❌ **绝不能共享** | 每端原生。这是整个架构里唯一「必须分端」的硬边界 |
| **L4 IPC** | ❌ 每端一套薄适配 | 桌面 Tauri Channel / Web WebSocket / 移动原生插件 |
| **L1 传输实现** | ❌ | ESP32 的 C 库和 tokio 没法共享 |

### 4.3 Rust core 怎么被其他端复用

| 目标端 | 方案 | 成熟度 |
|---|---|---|
| Desktop（Tauri） | 直接 `cargo add`，同进程 | ✅ 完美 |
| Web | 编译到 wasm32（core 要 `no_std` + 无 tokio） | ✅ 可行，注意去掉文件/网络依赖 |
| Android | **UniFFI** → Kotlin（官方支持） | ✅ 成熟 |
| iOS | **UniFFI** → Swift（官方支持） | ✅ 成熟 |
| Go 侧 | `uniffi-bindgen-go`（NordSecurity，第三方，132 star，基于 uniffi 0.31） | ⚠️ 能用但非官方 |
| **ESP32** | ❌ **不要**。交叉编译 + 内存 + esp-sr 是 C 库，收益为零 | ❌ |

**反过来的路线（如果 core 用 Go）**：
- 移动端用 `gomobile bind` → 但 **`gomobile bind` 对 cgo 支持有已知问题**（golang/go#35426），而音频库全都要 cgo。**这条路基本堵死。**
- 所以：**如果 core 要跨到移动端，用 Rust + UniFFI，别用 Go + gomobile。**

### 4.4 明说的取舍

**推荐组合 A（首选）：Tauri 2.x + Rust core + Web UI + 原生音频**

| 维度 | 评价 |
|---|---|
| 二进制 | ✅ 最小（3MB 级） |
| 移动端 | ✅ 官方支持，Rust core 可被 UniFFI 复用 |
| Web 端 | ✅ 前端代码直接复用 |
| 音频 | ✅ 原生 cpal，AEC 可做 |
| 粒子特效 | ✅ Canvas/WebGL 随便做 |
| **代价 1** | ⚠️ **Linux 上要写 wry/WebKitGTK 的平台代码**（开 media-stream、挂权限回调）——但既然音频走原生，这个坑其实可以不踩 |
| **代价 2** | ⚠️ Tauri 的 Android 权限要写 Kotlin（`MainActivity.kt`） |
| **代价 3** | ⚠️ Rust 学习曲线 + 编译慢（首次 5–10 分钟） |

**备选组合 B：Wails v3 + Go + Web UI + 原生音频（malgo）**

| 维度 | 评价 |
|---|---|
| 二进制 | ⚠️ 10–15MB（比 Tauri 大 3–5 倍） |
| 移动端 | ❌ **实验性**，官方明说不保证 |
| Web 端 | ✅ v3 有 `-tags server`，同一份代码起 HTTP 服务，Web 端直接跑 |
| 音频 | ✅ malgo 全平台（含 Android） |
| **代价** | ⚠️ v3 还是 beta（beta.34），API 还会变；Linux 要求 GTK4+WebKitGTK6.0，老发行版用户直接装不上 |
| **适用** | 团队 Go 熟、不需要移动端、能接受 15MB |

**备选组合 C（极致轻量/极致统一）：Rust + winit + wgpu 自绘**

| 维度 | 评价 |
|---|---|
| 二进制 | ✅ 估计 3–6MB（未实测） |
| 一致性 | ✅ 最高，一套渲染代码可编到 desktop + wasm |
| 粒子特效 | ✅ **最合适**——你的 UI 核心就是球+粒子，WGSL 直接写，比 WebView 还自由 |
| **代价** | ❌ UI 开发效率最低（没有现成组件、没有 CSS、没有热重载） |
| **代价** | ❌ 移动端要自己接 winit 的 android/ios 后端 |
| **适用** | UI 简单到只有「一个球+粒子+几行字」，且团队 Rust 很强 |

**我的建议**：**选 A**。理由是「移动端 + Web 端复用」这件事上 Tauri 有官方路径，而 Wails v3 的移动端官方自己都说是 experimental；而 C 的 UI 开发成本会让你在「调粒子颜色」上花掉本该做语音的时间。

## 5. 首版 MVP 建议

### 5.1 最小可行组合

```
Tauri 2.12.x（Rust）
├── 音频：cpal 0.18（采集 16kHz mono）+ rodio 0.23（播放）
├── AEC：先不做（MVP 用耳机，或用 cpal 直通）
├── 唤醒词：先不做（MVP 用全局快捷键 / 托盘点击触发）
├── 云端：tokio-tungstenite 连实时语音 WS API
├── UI：单个 HTML + Canvas 2D（不用 WebGL，先跑通）
│   └── 蓝色球 + 60 个粒子的径向频谱
└── IPC：tauri::ipc::Channel 每 16ms 推 64 个 f32
```

**MVP 明确不做的事**（这些都会拖死第一版）：
- ❌ 唤醒词（先用手动触发）
- ❌ AEC（先要求戴耳机）
- ❌ Linux（WebKitGTK 的坑留到第二版）
- ❌ 移动端
- ❌ ESP32
- ❌ 打断逻辑（先做「说完再答」）

### 5.2 先做哪一端

**先做 macOS 或 Windows（选你日常开发的那台）。**

理由：
- **Windows**：WebView2 是系统自带（Win10/11），Tauri 支持最好，`on_permission_request` 完整可用。缺点：WASAPI 延迟略高，要测 exclusive mode。
- **macOS**：CoreAudio 延迟最低（3–6ms），`VoiceProcessingIO` 一行开 AEC。缺点：签名/公证麻烦，Info.plist 要配。
- **Linux 放最后**：WebKitGTK 的 media-stream 默认关、权限默认拒、AppImage 里 GStreamer 版本还会和宿主冲突（真实案例：deepseek-harness-desktop PR #1220）。**这是三个平台里坑最多的。**

### 5.3 里程碑（建议顺序）

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| **M0**（1–2 天） | Tauri 空壳 + 一个 Canvas 画的蓝球在转 | `cargo tauri build` 出包，双击能开，球在动 |
| **M1**（3–5 天） | cpal 采集 → 算 FFT → IPC 推给 Canvas | 说话时粒子跟着跳；CPU < 10% |
| **M2**（3–5 天） | 接云端 WS，能发能收 | 说一句话，听到回复音频 |
| **M3**（3–5 天） | 全双工 + 打断 | 说话时能打断正在播放的 TTS |
| **M4**（1 周） | 加 AEC（webrtc-audio-processing） | 不戴耳机也不啸叫 |
| **M5**（1–2 周） | 加唤醒词（rustpotter 或 openWakeWord） | 喊「小蝶」能唤醒，误唤醒 < 1 次/小时 |
| **M6** | 托盘常驻 + 开机自启 | 关窗口不退出，托盘可呼出 |
| **M7** | 第二平台（Windows↔macOS 互换） | 同代码编译通过 |
| **M8** | Linux | 三个发行版能装 |
| **M9** | Web 端 | 浏览器打开能用（麦克风走浏览器原生） |
| **M10** | 移动端 | Tauri mobile 出包 |
| **M11** | ESP32 | C 固件，只实现「唤醒 + 推流 + 放音 + 简单频谱」 |

### 5.4 MVP 阶段就要定下来的事（定错了后面很贵）

1. **音频帧格式**：定 16kHz / mono / i16 / 20ms 帧（320 samples）。所有端统一。
2. **WS 协议**：控制帧 JSON，音频帧二进制（首字节区分类型）。ESP32 也按这个来。
3. **状态机枚举**：`Idle / Waking / Listening / Thinking / Speaking / Error`。六个数，所有端共用。
4. **频谱数据格式**：64 个 f32（0–1 归一化），16ms 一帧。UI 只认这个。
