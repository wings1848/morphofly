## 一句话

**一个开箱即用、不用按键的语音前台：喊一声「小蝶」就进入通话，用嘴指挥 DSH 干活，活干完它会主动回来说。**

---

## 1. 它到底解决什么问题

现在指挥 AI 干活，要开电脑、开窗口、打字、看屏幕。
**手被占着的时候（做饭、开车、躺在沙发上、修东西）就干不了。**

蝶梦要做的：把手解放出来。
- 不用看屏幕
- 不用按键
- 不用说「请帮我」这种客套话

**只解决一件事：说人话 → 派活 → 听结果。**

---

## 2. 用户故事

### 主场景

> 我打开电脑，蝶梦自己就在后台跑着。
> 我喊「小蝶」。
> 它回一个字：「在」。
> 我说「把登录页那个报错修一下」。
> 它说「好，已经派出去了」。
> 我继续干别的。
> 过一会儿它自己开口：「修好了，改了三个文件，测试都过了」。
> 我问「有没有副作用？」
> 它答「只动了登录模块」。

### 拆开看，9 条能力

| # | 能力 | 用户怎么说 | 优先级 |
|---|---|---|---|
| 1 | 唤醒 | 「小蝶」 | P0 |
| 2 | 进入/退出通话 | 点小球 / 再说一声 | P0 |
| 3 | 派活 | 「把 X 修了」 | P0 |
| 4 | 问进度 | 「那个弄完了吗」 | P0 |
| 5 | 打断 | 「停，先别改了」 | P0 |
| 6 | 追加需求 | 「顺便加个日志」 | P1 |
| 7 | 主动汇报 | 它自己开口说「好了」 | P0 |
| 8 | 切换工作目录 | 「换到家里云那个项目」 | P1 |
| 9 | 闲聊/陪伴 | 「今天好累」 | P2 |

## 3. 三个必须死守的设计原则

### 原则一：语音前台**只负责嘴和耳朵**

它做：听懂、澄清、整理成任务、转交、汇报、闲聊
它**不做**：规划、拆解、写代码、读文件、跑命令

**为什么**：如果它也能写代码，它就会开始自己干活，然后你就有了两个会干活的 Agent 互相打架。

**怎么保证**：靠**物理隔离**，不靠提示词自觉——
云端语音模型手上**根本不存在**文件读取、命令执行这些工具。
它有且只有 4 个函数（见《开发方案》）。

### 原则二：语音通道和任务执行**互不阻塞**

后台在跑 3 个任务，你照样能正常说话、随时插话。
- 语音连接断了 → 后台任务不受影响，继续跑
- 后台任务卡住 → 语音通道照常响应，能问「怎么了」

**为什么**：这两个是两种性质的东西。语音要的是**毫秒级**，任务要的是**分钟到小时级**。
混在一起，任何一个都会拖死另一个。

### 原则三：不需要说明书

打开软件就能用。
没有登录页、没有配置向导、没有「点击开始」按钮。
喊一声就通。

## 4. 明确「不做」的事

写在前面，防止范围膨胀：

| 不做 | 原因 |
|---|---|
| ❌ 语音前台自己写代码 | 见原则一 |
| ❌ 本地跑大模型 | 要轻量，模型在云端 |
| ❌ 多人/多设备同时用一个会话 | V1 单人单会话 |
| ❌ 语音购物的商业化闭环 | 先能用，再想钱 |
| ❌ 3D 虚拟形象 / Live2D 角色 | 用户要的是「蓝色小球」，不是虚拟主播 |
| ❌ 全离线可用 | 云端 API 是核心，断网就是不能说话 |
| ❌ V1 支持 ESP32 | V3 才做，V1 只做桌面 |
| ❌ 复杂多轮任务编排 UI | 语音里讲不清，交给 DSH |

## 5. 各端目标（分版本）

用户原话要求支持 web / 桌面 / 安卓 / iOS / ESP32。
**一次做不完，必须分期。**

| 版本 | 端 | 目标 | 预估 |
|---|---|---|---|
| **V1** | Windows / macOS / Linux 桌面 | 能唤醒、能派活、能汇报 | 4–6 周 |
| **V1.5** | Web（浏览器打开就能用） | 没装客户端也能试 | +1 周 |
| **V2** | Android / iOS | 手机随时能用 | +3 周 |
| **V3** | ESP32 小屏音箱 | 硬件形态 | 待评估 |

**关键判断**：V1 只做桌面。桌面跑通了，其它端只是「换个壳」，核心逻辑和协议不变。

## 6. 硬性指标

| 指标 | 目标 | 理想 | 怎么算达标 |
|---|---|---|---|
| 唤醒响应 | < 500ms | < 300ms | 喊完到听见「在」 |
| 端到端对话延迟 | < 800ms | < 500ms | 说完到听见回应（第一声） |
| 打断响应 | < 300ms | < 150ms | 说「停」到声音停止 |
| 常驻内存 | < 150MB | < 80MB | 空闲时 |
| 安装包体积 | < 100MB | < 40MB | 安装包大小 |
| 唤醒误触发 | < 1 次 / 8 小时 | — | 静默环境实测 |
| 唤醒漏检率 | < 5% | < 2% | 100 次喊，漏几次 |
| 每小时对话成本 | < ¥0.5 | < ¥0.2 | 连续说 1 小时 |

## 7. UI / 交互需求

### 视觉

- **一个科技感蓝色小球**，极简
- 待机时安静、几乎不占视线
- 通话时有**梦幻美丽的粒子动效**，让人一眼知道「它在听」
- 不要 3D 虚拟人，不要拟人化脸

### 交互

| 动作 | 结果 |
|---|---|
| 打开软件 | 后台常驻，小球出现，**不用按任何键** |
| 喊「小蝶」 | 进入通话模式，回「在」，粒子动效启动 |
| 点小球 | 进入 / 退出通话模式（开关） |
| 说话 | 随时打断它 |
| 安静一段时间 | 自动退出通话模式，回到待机 |

### 多端一致性

小球的样子在所有端**完全一样**。
桌面是悬浮小窗，Web 是网页右下角，手机是全屏中心。

## 8. 参考与借鉴

### yachiyo（第八千代）

用户提供的参考：[yachiyo.potatoya.cn](https://yachiyo.potatoya.cn)

**实测结论**：它是一个歌词同步 + 角色陪伴的 Windows/Android 客户端（109MB，Electron/Web 技术栈）。
**它没有语音能力**，也没有小球 UI。

**可以借鉴的**：
- 整体美学：暗色、克制、极简、动画细腻
- 产品气质：陪伴感、不说教
- 分发形态：一个安装包，装完就用，不折腾

**不该抄的**：
- 它的 Live2D 虚拟角色（我们要小球）
- 它的歌词同步（和语音无关）

### 其他视觉参考

- Apple Siri 光球（[分析](https://www.uisdc.com/hunter/0221632761.html)）
- [swiftui-orb](https://github.com/goetzrobin/swiftui-orb) — 参数化小球实现，配色与粒子给了很好的起点
- [AiVoiceOrb](https://pub.dev/documentation/ai_voice_orb/latest/ai_voice_orb/OrbTheme-class.html) — `glowColor #38BDF8` / `particleColor #FFFFFF`，和我们的色板接近

### 已有的地基

| 资产 | 位置 | 说明 |
|---|---|---|
| 既有架构设计 | `想法/语音交互前台架构.canvas` | **有 StepAudio 真机实测数据**，31 节点 |

| 家里云服务器 | wings-tx-us1 `100.99.51.5` | 7×24 常驻，可做中转 |

### 关键风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 云端实时语音模型价格波动大 | 成本不可控 | provider 可替换，配置化 |
| 主流模型延迟达不到 500ms | 体验打折 | 目标定 800ms，500ms 是理想值 |
| 唤醒词误触发 | 烦人 | 可调灵敏度 + 双击唤醒兜底 |
| DSH 委派 API 有权限约束 | 可能派不动活 | **阶段 0 先验证**，不通就换架构 |

## 10. 验收的整体标准（详细版见《验收标准》）

这个项目算做成了，当且仅当：

1. 我打开电脑，**什么都不按**，喊「小蝶」，它回「在」
2. 我说「把 X 修了」，它确认派出去了
3. 我说「停」，它立刻停
4. 活干完了，**它自己开口**告诉我
5. 整个过程我**没碰过键盘鼠标**
6. 连续说一小时，花费不到 5 毛

**这 6 条就是产品的定义。任何一条不满足，都还没做完。**
