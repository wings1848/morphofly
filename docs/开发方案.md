### 三条边界（都在进程/网络层，不靠自觉）

| 边界 | 手段 |
|---|---|
| 语音模型**不能**读写文件 | 云端模型手上只有 4 个自定义函数，物理上没有文件/命令工具 |
| 语音 App **不能**直接改代码 | 它只发消息给 DSH，DSH 才动文件 |
| 后台任务**不能**阻塞语音 | 两条独立连接，任务表异步读写 |

## 3. 核心状态机

```
                    ┌─────────────┐
        ┌──────────▶│   S0 待机    │◀──────────┐
        │           │ 小球暗、小    │           │
        │           └──────┬──────┘           │
        │                  │ 听到「小蝶」        │ 静音超时
        │                  ▼                  │ /点击关闭
        │           ┌─────────────┐           │
        │           │   S1 唤醒    │           │
        │           │ 亮脉冲+「在」 │           │
        │           └──────┬──────┘           │
        │                  │ 建立 WS 连接        │
        │                  ▼                  │
        │           ┌─────────────┐           │
        │      ┌───▶│   S2 聆听    │           │
        │      │    │ 粒子绕流     │           │
        │      │    └──┬───────┬──┘           │
        │      │       │       │ 检测到说完    │
        │      │       │       ▼              │
        │      │       │  ┌─────────────┐     │
        │      │       │  │   S3 思考    │     │
        │      │       │  │ 粒子内旋     │─────┘
        │      │       │  └──────┬──────┘
        │      │       │         │ 工具调用返回
        │      │       │         ▼
        │      │       │  ┌─────────────┐
        │      │       └──│   S4 说话    │
        │      │          │ 粒子外扩     │
        │      │          └──────┬──────┘
        │      │                 │ 说完
        │      └─────────────────┘
        │
        │           ┌─────────────┐
        └───────────│   S5 异常    │◀── 断网/API 失败
                    │ 暗、粒子散落  │
                    └─────────────┘
```

**状态迁移的硬约束**：

| 规则 | 原因 |
|---|---|
| S0 → S1 只由 KWS 或点击触发 | 不能因为噪音就醒 |
| S1 → S2 必须先连上云端 | 连不上就退回 S0 并提示 |
| S4 时用户说话 → 立即回 S2 | 打断是核心体验 |
| S2 静音 30s → 回 S0 | 省电、省钱 |
| 任何态 → S5 只由连接错误触发 | 区分「用户操作」和「系统故障」 |

## 4. 关键实现难点与解法

### 4.1 打断（barge-in）——最影响体验的一环

**问题**：如果等云端的 `speech_started` 事件走完一圈才停播，会延迟 200–400ms，用户会觉得「它不听我说话」。

**解法：本地先停，服务端后确认**

```
cpal 采集 → AEC → 本地 VAD
    │ 检测到本地有人声
    ▼
① 立刻停播放 + 清空 ring buffer   ← 本地做，不等人
    │
    ▼
② 向云端发送 input_audio_buffer.append（继续推流）
    │
    ▼
③ 云端返回 speech_started → 确认打断生效
```

**顺序不能错**：先停播放，再发 cancel。反过来用户会听到自己的回声。

**播放必须可「立即停止」**：用 ring buffer + 可中断的播放循环，
不能一次性把整段 PCM 排给声卡。

### 4.2 回声消除（AEC）——**必须走原生**

**⚠️ 这是推翻原方案的关键点。**

原方案想用 WebView 的 `echoCancellation: true`，**行不通**：

| 问题 | 后果 |
|---|---|
| 拿不到 AEC 参考信号 | 播放走 WebView、采集走原生 → 参考信号断链，AEC 失效 |
| Linux WebKitGTK 默认关 media-stream | 麦克风根本用不了 |
| iOS `AnalyserNode` 对 getUserMedia 流返回全 0 | 可视化归零 |
| 延迟不可控 | 要过浏览器音频服务层 |

**正确做法：音频全原生，AEC 自己接参考信号**

```
cpal 采集 16kHz mono i16
  → webrtc-audio-processing（AEC3，用「正在播放的 TTS」当 reference）
  → VAD / 唤醒词
  → WebSocket 发云端
  ← WebSocket 收 PCM
  → 一路给 rodio 播放
  → 一路喂回 AEC 当 reference      ← 这条是关键
```

**AEC 的硬要求**：
1. **同一设备、同一采样率、同一时钟**。别一边 48k 一边 16k，重采样会引入未知延迟，AEC 的延迟估计会崩。
2. **reference 必须是「真正送到扬声器的那一路」**，中间有音量调节、重采样，reference 都要跟着变。
3. **Linux 上别用 ALSA 直连**（独占会 `Device or resource busy`），走 PulseAudio/PipeWire。

**MVP 可先降级**：要求戴耳机，跳过 AEC。但架构上要留好 reference 通道。

### 4.3 音频库与格式

| 用途 | 库 | 说明 |
|---|---|---|
| 采集+播放 | **cpal 0.18.2 + rodio 0.23.0** | rodio 0.23 新增 microphone 模块 |
| AEC/降噪 | **webrtc-audio-processing 2.1.0** | AEC3+NS+AGC+VAD 全套，10ms 帧 |
| 代价 | 编译要 clang/meson/ninja，二进制 +2–5MB（未实测） | |

**格式约定（MVP 就定死，ESP32 也照这个来）**：

| 环节 | 格式 |
|---|---|
| 采集 | **16kHz / mono / i16 / 20ms 帧** |
| 上行 | 同采集（不重采样） |
| 下行 | PCM 24kHz（Qwen 输出） |
| 播放 | ring buffer，200–500ms 余量抗抖动 |

**全双工注意**：播放侧写 ring buffer，采集侧固定 10/20ms 一帧喂 AEC。

### 4.4 WebSocket 连接（Key 不进前端）

**Key 放哪**：Rust core 侧，前端完全拿不到。

```
WebView ──IPC──▶ Rust Core ──WS + Authorization──▶ Qwen
        (只有频谱数字)      (带 Key)
```

**顺带的好处**：
- API Key 不进前端产物（可 grep 验证）
- 可做重连、限流、日志
- 换 provider 不用改前端

**Tauri IPC 带宽**：64 bin × 4 byte × 60fps = 15KB/s，不是瓶颈。

### 4.5 通知回灌 vs 打断的冲突

**问题**：DSH 干完活要主动汇报，但此时用户可能正在说话。直接 `response.create` 会**打断用户**。

**解法：排队 + 状态判断**

```
DSH 回调 notify_voice_agent
    │
    ▼
查当前状态：
  · S0 待机 → 直接唤醒 + 汇报（这是我们要的）
  · S4 说话 → 排队，等 response.done
  · S2 聆听（用户在说）→ 排队，等用户说完
  · S3 思考 → 排队
```

惩罚：句子里加「顺便说一下」作为过渡，避免突兀。

### 4.6 唤醒词常驻监听很费电

**问题**：一直开麦采集 + 跑 KWS，笔记本电池撑不住。

**解法：分档**
| 场景 | 策略 |
|---|---|
| 插电 / 台式 | 常驻监听 |
| 电池 | 降采样率（16k→8k 做 KWS） |
| 息屏/休眠 | 暂停，恢复时重启 |

**P1 先做插电常驻，省电策略 P2 再说。**

## 5. 与 DSH 的接口契约

### 5.1 语音 → DSH（4 个工具）

```jsonc
// 1. 派活
{
  "name": "delegate_task",
  "description": "把一个任务交给编码 agent 执行。立即返回，不等待完成。task 必须自包含——对方看不到我们的对话历史。",
  "parameters": {
    "task":    { "type": "string", "description": "完整、自包含的任务描述，含项目路径与具体要求" },
    "dir":     { "type": "string", "description": "工作目录，可选" },
    "urgent":  { "type": "boolean" }
  }
}

// 2. 查进度
{
  "name": "query_progress",
  "parameters": {
    "task_id": { "type": "string", "description": "省略则返回全部进行中的任务" }
  }
}

// 3. 取消
{
  "name": "cancel_task",
  "parameters": {
    "task_id": { "type": "string" }
  }
}

// 4. 追加需求
{
  "name": "append_requirement",
  "parameters": {
    "task_id": { "type": "string" },
    "extra":   { "type": "string" }
  }
}
```

### 5.2 DSH → 语音（1 个回调）

```jsonc
{
  "name": "notify_voice_agent",
  "parameters": {
    "task_id": { "type": "string" },
    "status":  { "type": "string", "enum": ["done", "failed", "blocked", "needs_decision"] },
    "summary": { "type": "string", "description": "一两句人话，会被直接念出来，别写代码块" }
  }
}
```

**`summary` 的硬要求**：会被 TTS 念出来，所以
- 不能有代码、路径、URL
- 不能有 markdown 符号
- 一句话说清「做了什么 + 有没有问题」

### 5.3 任务表结构

```go
type Task struct {
    ID        string    // task_20261023_1830_ab12
    Goal      string    // 用户原话（整理后）
    Dir       string
    Status    TaskStatus // pending|running|done|failed|cancelled|blocked
    Summary   string    // 最近一次汇报
    AgentID   string    // DSH 那边的 handle
    CreatedAt time.Time
    UpdatedAt time.Time
}
```

**持久化**：落到 `~/.diemeng/tasks.json`，重启不丢。

## 6. 开发阶段划分

### 阶段 0 · 打通接缝（2–3 天）

**这一阶段决定整个方案成立不成立。不通过就换架构，别硬做。**

| 任务 | 验收 |
|---|---|
| 0.1 建 Rust + Tauri 骨架 | `cargo tauri dev` 能弹窗 |
| 0.2 **cpal 原生采集**跑通 | 打印实时音量，**不经 WebView** |
| 0.3 rodio 播放跑通 | 放一段 edge-tts 音频 |
| 0.4 Rust 侧 WS 连 Qwen | 发一段音频，收到文字回复 |
| 0.5 频谱推给 WebView 画球 | 球随音量跳动（64 float @60fps） |
| 0.6 验证 DSH ACP 连接 | 能 create session 并收到回复 |
| 0.7 验证 DSH 能否接收外部任务 | 派一个「列目录」任务，能拿到结果 |

**通过标准**：这 7 条全绿。任一红，停下来重新设计。

> **0.2 是新增的关键项**。原方案想用 WebView 采音，已被否决。
> 这一条必须证明「原生采集 → AEC reference → 播放」这条链能闭环。

**平台顺序建议**：先做 **macOS 或 Windows**，Linux 放最后（三个平台里坑最多）。

### 阶段 1 · 能说话（3–5 天）

- 完整双工音频链路（cpal 采集 → 云端 → rodio 播放）
- ring buffer 播放 + 可中断
- 小球渲染 + 基础呼吸动效
- 点小球进出通话模式
- 有字幕（调试用）

**本阶段先不做 AEC**，要求戴耳机测试。

**验收**：点小球，说「你好」，听到回应。有延迟数字记录。

### 阶段 2 · 能派活（3–5 天）

- 4 个工具声明 + 实现
- 任务表
- 说话能派活到 DSH
- 能问进度

**验收**：说「列一下我的项目目录」，DSH 真的执行，语音回报结果。

### 阶段 3 · 能自动汇报（2–3 天）

- `notify_voice_agent` 回调
- 通知排队与打断协调
- DSH 干完主动开口

**验收**：派活后不管它，干完它主动说。

### 阶段 4 · 唤醒词（3–5 天）

- 集成 sherpa-onnx KWS
- 「小蝶」唤醒 + 回「在」
- 误触发/漏检率测量

**验收**：喊 100 次，漏 ≤5 次；静默 8 小时，误触发 <1 次。

### 阶段 4.5 · 加 AEC（2–3 天）

- 集成 webrtc-audio-processing
- 把「正在播放的 TTS」接成 reference
- 外放测试：不自我打断

**验收**：外放音量 70%，说「停」能正常打断，不被自己的回声触发。

### 阶段 5 · 打磨（5–7 天）

- 完整粒子动效（五个状态）
- 打断优化
- 断线重连
- 打包分发

**验收**：跑完整验收表。

### 阶段 6+ · 扩展（后续）

- Web 端
- 移动端
- ESP32

## 8. 不变量（开发期间不许破坏的东西）

| # | 不变量 | 检查方式 |
|---|---|---|
| 1 | 语音模型只有 4 个工具，不多不少 | 代码审查 + 运行时断言 |
