## 0. 一句话结论

| 层 | 选择 | 理由 |
|---|---|---|
| 实时语音 | **阿里云百炼 qwen3.8-omni-flash-realtime** | 国内直连、中文最好、最便宜、支持工具调用 |
| 备选语音 | Google Gemini Live | 能力更强但贵约 16 倍、需代理 |
| 唤醒词（桌面/移动/Web） | **sherpa-onnx KWS** | 中文改文本即可换词，**实测「小蝶」能识别** |
| 唤醒词（ESP32） | **esp-sr WakeNet** | sherpa-onnx **在 ESP32 上跑不了**，必须双引擎 |
| 客户端壳 | **Tauri 2.x（Rust）** | 体积最小、移动端官方支持、UniFFI 可复用 core |
| **音频** | **cpal + rodio + webrtc-audio-processing（全原生）** | WebView 采音会断掉 AEC 参考信号 |
| UI | WebView 里 Canvas/WebGL | 只收频谱数字，**永不碰麦克风** |
| 协议 | WebSocket（JSON 控制帧 + 二进制音频帧） | 所有候选模型都是这套，不绑死 |
| ESP32 | **C/C++（ESP-IDF + esp-sr + LVGL）** | Go/Rust 内存与闭源库都不允许 |
| 测试音频 | **edge-tts** | 免费、已实测跑通、中文音色自然 |

**一句话**：**Rust 写 core 和音频，WebView 只画球，Tauri 做壳。**

### 1.2 价格对比（**含上下文累积**，2026-10-23 修正）

> ⚠️ **本节已重算。原结论「Qwen 比 Gemini 便宜 15–20 倍」是错的。**
> 错在两点：① Gemini 官方有按分钟计价（$0.005/$0.018 每分钟），我误按 token 单价硬套；
> ② **Qwen 每轮会把历史对话重新作为输入计费**，我漏算了这一块。

**关键区别：两类计费模型**

| 类型 | 计费方式 | 谁属于 |
|---|---|---|
| **A 类（按流计时）** | 只按实际音频时长收费，**不重发历史** | Gemini、GLM、GPT-Live-1 |
| **B 类（按 token 累积）** | 每轮把**全部历史**重新计费，轮次越多越贵 | **Qwen**、豆包、StepAudio、OpenAI Realtime |

**假设**：1 小时对话 = 用户说 30 分钟 + AI 说 30 分钟，共 150 轮。
Qwen 官方换算率：输入音频 **7 token/秒**，输出音频 **12.5 token/秒**。
Qwen 音频历史上限 **600 秒**（超过就截断，这是它便宜的核心原因）。

| 模型 | 计费类型 | 单轮直算 | **含累积（真实）** | 折算 |
|---|---|---|---|---|
| **qwen3.8-omni-flash-realtime** | B | ¥0.35 | **≈ ¥3.8** | ≈ $0.53 |
| **Gemini 3.8 Live** | A | — | **≈ ¥5.0** | ≈ $0.69 |
| 豆包 Doubao Realtime | B | ¥14.4 | **≈ ¥18.6** | ≈ $2.58 |
| StepAudio-2.5-Realtime | B | ¥3.3 | ≈ ¥6.0 | ≈ $0.83 |
| GLM-Realtime-Flash | A | ¥10.8 | ¥10.8 | ≈ $1.50 |
| GPT-Live-1 | A | $3.0 | $3.0 + 后端费 | ≈ ¥21.6 |
| GPT-Realtime-2.1 | B | $2.88 | ≈ $3.42 | ≈ ¥24.6 |
| 讯飞超拟人 | 套餐 | ¥8–12 | ¥8–12 | ≈ $1.1–1.7 |

**真实结论**：
- Qwen 仍是**最便宜的**，但只比 Gemini 便宜 **约 1.3 倍**，不是 15–20 倍。
- Qwen 比豆包便宜约 **4.9 倍**——这个差距是真的。
- 所以「选 Qwen」的理由要从「碾压性便宜」改为「**便宜 + 国内直连**」。

**如果对话很短（10 轮以内）**，Qwen 单轮成本 ¥0.35/小时，优势会明显拉大。
**如果聊很久（>100 轮）**，Qwen 靠 600 秒音频历史截断守住成本。

> 阿里官方口径「一轮约 ¥0.0025」指的是**单轮**，不是连续一小时。
> 原文档把这两个混用了，特此更正。

### 1.3 为什么选 Qwen

**优点**
1. **全场最便宜**——含累积约 ¥3.8/小时，比豆包便宜约 4.9 倍
2. **国内直连**——不用代理，延迟稳定，不卡在墙外（**这条现在是最强理由**）
3. **中文最强**——113 语种识别 / 36 语种合成，默认 Tina 音色，支持声音复刻
4. **工具调用最完整**——自定义 Function Calling + 远程 MCP + 联网搜索（后两者与 FC 互斥）
5. **原生多模态**——同一路 WS 里推图片/视频帧，可开 `representation_compact` 省 3/4 token
6. **有实测数字**——不是 PPT，是别人真跑出来的

**缺点 / 风险**
1. 首音频 1.37s，**达不到 500ms 理想值**（官方模型级 211ms 不含网络）
   - 官方自己说：「如果业务要求 500 毫秒以内，需要在端上做流式采集和播放缓冲」
   - 应对：目标定 800ms（可接受），500ms 作为优化方向
2. 工具调用会把一轮拉长到 4s 左右
   - 官方建议：「要给用户一个『正在查』的反馈，否则 4 秒会被感知成卡顿」
   - 应对：**思考态要立刻给视觉反馈**（见 UI 设计的 S3 态）
3. 模型名带版本号，**会过期**
   - 应对：模型/端点/密钥全走配置

### 1.3.5 限流与区域限制（**新发现，会翻车**）

| 项 | 现实 | 影响 |
|---|---|---|
| **Qwen 限流** | **60 RPM** / 2,000,000 TPM | 每秒只能建 1 个会话。**并发用户超 60 就排队**，必须提前提工单扩容 |
| **豆包限流** | QPM 60 / TPM 100,000 | 音频 token 消耗快，多路并发很快打满；并发要另买 |
| **Gemini 区域** | 官方可用地区列表**不含中国大陆** | 必须代理，且违反 ToS 有封号风险 |
| **OpenAI 区域** | 同上，不含中国大陆 | 同上 |

**结论**：Gemini/OpenAI 不只是贵，而是**在中国大陆不可用**。
这比价格更决定性地排除了它们——我们做的是中文语音助手。

**Qwen 的 60 RPM 要注意**：V1 单人用完全够（一个会话跑一天），
但如果将来做多用户，必须提前扩容。

### 1.4 实测协议细节（踩坑清单）

从阿里官方文档 + 阶跃实测经验汇总：

| 坑 | 说明 |
|---|---|
| 输出模态决定事件名 | 只开文本收 `response.text.delta`；带音频收 `response.audio_transcript.delta` |
| ~~VAD 对合成音频不友好~~ | **2026-10-23 实测更正**：edge-tts 生成的音频**有尾部静音**（实测 0.56–1.39s），反而对 VAD 友好，**不用手动补**。阿里文档说的「TTS 音频结尾没停顿」指的是**别的 TTS**，不适用于 edge-tts |
| 音频格式 | 输入 PCM 16kHz 单声道；输出 WAV 24kHz |
| 端点结构 | `wss://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api-ws/v1/realtime?model=...` |
| 鉴权 | 百炼 API Key，握手头 `Authorization: Bearer ...` |
| 浏览器限制 | 浏览器原生 WS **不能设握手头** → 必须走 Host 中转 |
| MCP 工具发现是异步的 | `session.updated` ≠ 工具可用，要等 `mcp_list_tools.completed` |
| `response.create` 会打断 | 有 in-flight 回复时要排队，等 `response.done` |
| **WS 地址必须带 WorkspaceId** | 是 `{WorkspaceId}.cn-beijing.maas.aliyuncs.com`，**不是**通用的 `dashscope.aliyuncs.com`。很多人卡在这 |
| **联网搜索与工具调用互斥** | `enable_search` 和 `session.tools` 不能同时开 |
| **上下文累积计费** | 每轮重发全部历史。**必须设轮数上限或定期开新会话**（官方明确建议） |
| **3.8 音频+文本双计费** | `qwen3.8` 的音频和对应文本**分别计费**；3.5 系列只算音频。别拿 3.5 报价套 3.8 |
| **音频历史只有 600 秒** | 超过就截断（这是它便宜的原因，但也意味着长对话会「忘事」） |

**如果将来换豆包，额外要注意**（调研发现）：
- 豆包有**两代协议**：旧版是二进制帧（4 字节 header + payload），新版 Seeduplex 是纯 JSON。**别照旧教程写**
- 必须严格按 20ms 节奏发音频，偏离会**直接报错**
- 关麦要发 `input_audio_mute.commit`，否则超时
- 必须发 `session.close` 等回复再断连，直接断会报 `ContextCanceled`

## 2. 唤醒词检测（KWS）

### 2.1 为什么这是个难点

需求是「喊小蝶就醒」，且要覆盖 **桌面 + 手机 + ESP32**。
市面方案大多只解决其中一部分。

### 2.2 候选对比

| 方案 | 中文自定义词 | Go | Rust | ESP32 | 模型体积 | 结论 |
|---|---|---|---|---|---|---|
| **sherpa-onnx KWS** | ✅ 改文本即可 | ✅ cgo | ✅ crate | ❌ **跑不了** | **8.4MB** | **桌面/移动选它** |
| **esp-sr WakeNet** | ⚠️ 内置 35 个中文词，无「小蝶」 | ❌ | ❌ | ✅ **唯一可行** | ~几百 KB | **ESP32 只能用它** |
| openWakeWord | ⚠️ README 明写「只支持英文模型」 | 需 FFI | 需 FFI | ⚠️ 理论可行 | 11MB | 训中文要几万条样本，太重 |
| Porcupine | ✅ 但**内置中文词只有 4 个** | ❌ 无官方 | ❌ 无官方 | ❌ 官方明确不做 | ~1MB | **直接放弃**（见下） |
| snowboy | ❌ **训练站已关，无法生成新词** | — | — | — | — | **彻底死了**（2021-10 停更） |
| whisper.cpp | ⚠️ 非 KWS | ✅ | ✅ | ❌ | 75MB+ | 方向不对，常驻太耗 |
| Vosk | ✅ 改词表 | ✅ | ✅ | ❌ | **43.9MB** | 是 ASR+语法约束，不是专用 KWS |
| FunASR KWS | ⚠️ 有限 | ❌ | ❌ | ❌ | 未查证 | 流式是「句尾返回」，不是逐包唤醒 |

### 2.2.1 为什么淘汰 Porcupine 和 snowboy

**Porcupine（Picovoice）**——四个致命问题：
1. **内置中文唤醒词只有 4 个**（你好 / 咖啡 / 水饺 / 豪猪），「小蝶」要自定义 → 要钱
2. **免费额度 2026-06-30 已取消**，官方 FAQ 明说「没有面向个人或非商业的方案」
3. **无官方 Go/Rust SDK**：社区 `charithe/porcupine-go` 只有 16 star 且 2018 年停更；`pv_porcupine` crate 已 yanked
4. **ESP32 官方明确不做**（issue #321/#106：要有大客户出钱才考虑）

**snowboy**——**彻底死了**：
- 训练站 `snowboy.kitt.ai` 已下线，**无法生成任何新唤醒词**
- 最后提交 2021-10
- 只能用它自带的几个旧模型，做不了「小蝶」

### 2.3 选 sherpa-onnx 的理由

1. **改一个文本文件就能换唤醒词**——不用训练、不用等、不用花钱
2. **自定义词流程清楚**：用 `sherpa-onnx-cli text2token --tokens-type ppinyin` 把「小蝶」转 token
3. **和 DSH 已有技术栈重合**——DSH 的语音输入用的就是 sherpa-onnx（SenseVoice），团队已熟悉
4. **一个引擎干多件事**：KWS + VAD + ASR 都能做，减少依赖

### 2.3.1 **实测数据（本机真跑，2026-10-23）**

> 完整过程见 `唤醒词与TTS调研.md`。**这些不是官方宣传，是自己跑出来的。**

**模型**：`sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20`（中英双语，int8）

| 文件 | 大小 |
|---|---|
| encoder int8 | 4.4 MB |
| decoder | 742 KB |
| joiner int8 | 85 KB |
| en.phone | 3.2 MB |
| tokens.txt | 1.9 KB |
| **合计** | **8.4 MB** |

**「小蝶」转唤醒词（实测输出）**：

```bash
printf '小蝶 @小蝶\n' > keywords_raw.txt
sherpa-onnx-cli text2token --tokens tokens.txt \
  --tokens-type ppinyin keywords_raw.txt keywords.txt
# 输出：x iǎo d ié @小蝶
```

**实测性能**：

| 指标 | 实测值 | 条件 |
|---|---|---|
| **CPU 占用** | **单核 3.1%** | 13.1s 音频处理耗时 0.40s |
| 内存 | 86 MB RSS | 含 Python + onnxruntime 进程 |
| **唤醒延迟** | **1.1s 触发** | chunk-16；「小蝶」说完约 0.55s |
| 低延迟模式 | **0.9s 触发** | chunk-8，延迟 160ms |
| **召回** | **7/7 全中** | 7 条应唤醒音频 |
| **误唤醒** | **1/6** | 只有「小蝶儿真可爱」被误触发 |
| **长语音误报** | **0** | 47.6s 连续说话无唤醒词 |
| 噪声鲁棒 | 6/6 命中 | SNR 5dB 和 15dB 都全中 |
| 音量鲁棒 | 7/7 命中 | 增益降到 3% 仍能识别 |

**阈值结论**：`keywords_threshold` 从 0.15 到 0.5 结果几乎一样；
把 `keywords_score` 调到 2 或 3 反而会漏掉快语速的「小蝶」。
**官方默认值就是最优**：`keywords_score=1.0, keywords_threshold=0.25`。

**实测发现的两个短板**：
1. ~~「小蝶儿」会误唤醒——调阈值解决不了~~ → **已解决！见下**
2. **超快语速的孤立「小蝶」会漏**（0.7s 内说完）；但同样语速放在长句里能识别——模型依赖上下文，孤立短词最难

### 2.3.2 **关键突破：`num_trailing_blanks=4`**（2026-10-23 实测）

> 完整报告见 `唤醒词优化实测.md`

**把 `num_trailing_blanks` 从默认 1 改成 4：**

| 配置 | 召回 | 误唤醒 |
|---|---|---|
| `num_trailing_blanks=1`（默认） | 8/8 | **1/8**（小蝶儿） |
| **`num_trailing_blanks=4`** | **8/8** | **0/8** ✅ |

**延迟零代价**（nb=4 与 nb=1 检测时间都是 1.12s）。

**原理**：该参数要求关键词后连续出现 N 帧 blank 才触发。
「小蝶」说完后是静音 → 正常触发；「小蝶儿」的「儿」紧接着产生 token → blank 连不起来 → 被抑制。
**这是一个天然的近音词过滤器。**

**安全区间 4–10**，≥12 会漏检连续语音（实测 nb=12 漏检）。

**推荐的完整配置**：
```python
num_threads=1,
keywords_score=1.0,          # 保持默认，调高会破坏效果
keywords_threshold=0.25,     # 保持默认，实测不敏感
num_trailing_blanks=4,       # ★ 关键
```

**所以不必换成「小蝶小蝶」了**——两字「小蝶」配合 nb=4 已够用。

**语言绑定（已核实目录存在）**：

| 平台 | 路径 | 备注 |
|---|---|---|
| Go | `go-api-examples/keyword-spotting-from-file` | **需 cgo** |
| Rust | `rust-api-examples/run-keyword-spotter.sh` | crates.io 1.13.8 |
| C | `c-api-examples/kws-c-api.c` | 最底层，任何语言可 FFI |
| Android / iOS / Flutter / Web / C# / Java | 均有官方示例 | Web 走 WASM |

- 官方 KWS 模型页：<https://github.com/k2-fsa/sherpa-onnx/releases/tag/kws-models>

### 2.4 关键风险：两个字太短

「小蝶」只有两个音节。唤醒词的行业经验是 **3–4 个音节**最稳（区分度够、又不拖沓）。

**建议**
- 主要用「小蝶」（用户明确要求）
- 但**留配置项**，可切成「小蝶小蝶」
- 灵敏度做成用户可调滑块
- 提供**双击小球**作为兜底唤醒（误触发烦人时的退路）

**已准备专门的谐音负样本**（`test-audio/`）：

| 文件 | 内容 | 风险 |
|---|---|---|
| `14_neg_hudie.mp3` | 蝴蝶 | **谐音陷阱，最可能误触发** |
| `15_neg_xiaode.mp3` | 小的 | **谐音陷阱** |
| `13_fp_xiaodieer.mp3` | 小蝶儿 | 边界情况（可接受唤醒） |
| `12_neg_near_miss.mp3` | 近似词 | 泛化测试 |

**实测结论**：`num_trailing_blanks=4` 后，这一组**全部正确忽略**（误唤醒 0/8）。
**不需要换词。**

## 3. 客户端框架

> ⚠️ **本节已被专项调研推翻并重写（2026-10-23）。**
> 原结论「Wails v3 + WebView 采音」**作废**。
> 完整证据见 `技术选型调研-详版.md`（494 行）。

### 3.1 一句话

**桌面端 Tauri 2.x（Rust）做壳 + 音频全部走原生（cpal/rodio）+ UI 用 Web 画粒子。**
**WebView 只收频谱数字，永远不碰麦克风。**

### 3.2 为什么推翻原方案（三条死路）

**死路 1：AEC 拿不到参考信号 —— 这条是致命的**

回声消除的本质是「我知道我正在播什么，从麦克风里减掉它」。
如果播放走 WebView、采集走原生（或反过来），参考信号就**断链**，AEC 直接失效。

而我们要做**可打断的全双工**——没有 AEC，外放时会自己打断自己。

**死路 2：Linux 上根本跑不起来**

WebKitGTK 的 `enable-media-stream` **默认关闭**，权限回调**默认拒绝一切**。
真实案例：unsloth 的 Tauri 桌面版在 Ubuntu 上麦克风完全用不了。

**死路 3：iOS 的可视化会归零**

iOS 18 及以前，`AnalyserNode.getByteFrequencyData()` 对 `getUserMedia` 流**返回全 0**。
——我们的「粒子随声音跳动」直接没了。

**另外**：延迟不可控（要过 Chromium/WebKit 音频服务层）、权限模型三平台三套、
开发模式与打包后行为还不一致（Wails issue #4270）。

### 3.3 正确架构

```
cpal 采集 16kHz mono i16
  → webrtc-audio-processing（AEC，用「正在播放的 TTS」当 reference）
  → VAD / 唤醒词
  → WebSocket 发云端
  ← WebSocket 收 PCM
  → 一路给 rodio 播放
  → 一路喂回 AEC 当 reference
  → 每 16ms 算一次 FFT，把 64 个 float 通过 IPC 推给 WebView 画粒子
```

**WebView 只干一件事**：收 64 个 float，画球和粒子。

**IPC 带宽够不够**：64 bin × 4 byte × 60fps = **15KB/s**，完全不是瓶颈。

### 3.4 框架对比（2026-10-23 快照）

| 框架 | 版本 | 体积 | 移动端 | 音频 | 判断 |
|---|---|---|---|---|---|
| **Tauri 2** | 2.12.5 | 官方 <600KB<br>社区 hello world 3.2MB | ✅ 官方稳定 | ✅ 原生外挂 | **选它** |
| Wails v3 | 3.0.0-beta.34 | 10–15MB | ⚠️ 官方称 experimental | ✅ malgo | 备选（Go 熟时） |
| egui/eframe | 0.37.0 | **本机实测 5.98MB** | ⚠️ Android 有 PR | 需外挂 | 备选 |
| iced | 0.14.0 | 未查证 | ❌ 官方说不为移动设计 | 需外挂 | 淘汰（近 11 月未发版） |
| Slint | 1.18.1 | 未查证 | ✅ | 需外挂 | ⚠️ **嵌入式商用要买许可** |
| Fyne | 2.8.2 | 30–40MB | ✅ | ❌ 无内置 | 淘汰 |
| Gio | 0.10.3 | 未查证 | ✅ | ❌ 无内置 | 淘汰 |
| Flutter（参照） | 3.47.7 | 20MB+ | ✅ | ✅ 生态成熟 | 备选（非 Go/Rust） |

**Tauri 的取舍**
- ✅ 二进制最小、移动端官方支持、Rust core 可被 UniFFI 复用
- ⚠️ Linux 要写平台代码（但音频走原生后这坑可不踩）
- ⚠️ Android 权限要写 Kotlin
- ⚠️ Rust 学习曲线 + 首次编译 5–10 分钟

### 3.5 音频库选型

| 用途 | Rust | Go |
|---|---|---|
| 采集+播放 | **cpal 0.18.2 + rodio 0.23.0** | malgo v0.11.26（需 cgo） |
| AEC/降噪 | **webrtc-audio-processing 2.1.0** | ⚠️ 只有社区 cgo 封装 |
| 备注 | rodio 0.23 新增 microphone 模块 | oto v3.5.1 **只播放不采集** |

**Go 侧没有官方 WebRTC APM 绑定**，只有社区 cgo 包。
这是选 Rust 的又一个理由。

### 3.6 跨端复用（关键修正）

| 目标端 | 方案 | 成熟度 |
|---|---|---|
| Desktop | Rust crate 同进程 | ✅ 完美 |
| Web | 编译 wasm32（core 需 no_std） | ✅ 可行 |
| Android/iOS | **UniFFI** → Kotlin/Swift | ✅ 官方支持 |
| ESP32 | ❌ 不要复用 | 见下 |

**⚠️ 重要修正：Go + gomobile 这条路基本堵死。**
`gomobile bind` 对 cgo 有已知问题（golang/go#35426），而音频库全都要 cgo。
**core 要跨到移动端，必须用 Rust + UniFFI。**

### 3.7 ESP32：Go 和 Rust 都不现实

**TinyGo 在 ESP32-S3 上的硬数据**：

| 指标 | 数值 |
|---|---|
| 可用 DRAM | **416 KB** |
| 堆上限 | **298 KB** |
| PSRAM | **链接脚本完全不支持**（PR #5554 未合） |
| GC | 保守式（实时音频会爆音） |
| goroutine 栈 | 固定 8KB 不增长 |
| 唤醒词 | **无任何 Go 引擎**（WakeNet 是闭源 C 库） |

**Rust 能跑 I2S，但绕不开 C**：`esp-sr`（WakeNet/AFE）是乐鑫闭源 C 静态库，无 Rust 绑定。
既然要为它写 C 胶水，不如整体用 C。

**资源硬需求（乐鑫官方 benchmark）**：
单麦+参考+WakeNet9 = **60.1KB 内部 RAM + 739.7KB PSRAM**，CPU 8.8%。
→ **8MB PSRAM 是硬需求**。

**显示约束**：240×240 圆屏 SPI 总线物理上限 **30fps**。
Seeed 从 9fps 优化到 30fps 花了五轮调优。
→ 「梦幻粒子」在 ESP32 上最多 25–30fps，且必须 LVGL 逐像素画。

### 3.7.1 ESP32 的「小蝶」唤醒词怎么办（**要你决定**）

**问题**：esp-sr 内置 94 个唤醒词，中文 **35 个**，**没有「小蝶」**。

三条路：

| # | 方案 | 成本 | 说明 |
|---|---|---|---|
| 1 | **先用近似词验证** | 免费 | `wn9_hixiaoxing_tts`（Hi小星）或 `wn9_haixiaowu_tts`（Hi小巫），先把链路跑通 |
| 2 | **去官方 issue 申请** | 免费 | [esp-sr#88](https://github.com/espressif/esp-sr/issues/88)，官方说 TTS 训练能到人工样本的 95–98%，商用免费。门槛：有项目链接或被 5 人点赞 |
| 3 | **付费定制** | **金额未知** | 官方只收一次性定制费、不按量收 License。**具体价格查不到，要发邮件 sales@espressif.com 谈** |

**建议**：V3 之前不用管。等 V1/V2 跑通了再决定。

**结论**：ESP32 端用 **C/C++（ESP-IDF + esp-sr + LVGL）**，只共享协议层。
**V3 之前不必纠结。**

## 5. 与 DSH 的集成方式

### 5.1 DSH 已有的能力（重要发现）

DSH 已经内置了语音输入实验包：

| 包 | 作用 |
|---|---|
| `dsh-experimental-voice-input-bundle` | 浏览器麦克风 + 语音识别，启用后 Web 侧栏出现麦克风按钮 |
| `dsh-experimental-speech-to-text-sensevoice` | 本地 SenseVoiceSmall ONNX，**CPU 跑，不用 Python** |
| `dsh-experimental-api-speech-to-text` | 加过权的中转 Remote |

**意义**：不用从零做起。V1 可以先复用它的识别链路，只需要补「实时双工 + 唤醒 + 小球 UI」。

### 5.2 三种接入方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. DSH 插件** | 写 Cordis 插件，挂进 Web GUI | 和 DSH 一体，共享会话 | 绑死 Web，做不了独立 App |
| **B. ACP 客户端** | 蝶梦作为 ACP client，`dsh --profile acp` 当后端 | 标准协议，独立进程 | 需要管进程生命周期 |
| **C. SDK/JSON-RPC** | `dsh --profile sdk` 走 JSON-RPC stdio | 最灵活 | 要处理 stdio 管道 |

**建议：B + A 组合**
- 独立 App 用 **B（ACP）**——标准、解耦、DSH 挂了 App 还在
- 想在 DSH Web GUI 里用时，加个 **A（插件）**——复用同一套 Core

### 5.3 委派工具的定义（4 个）

语音前台只有这 4 个函数，**多一个都不给**：

| 函数 | 参数 | 后端动作 |
|---|---|---|
| `delegate_task` | `{task: string, dir?: string}` | 投递到 DSH 主会话，**立即返回不阻塞** |
| `query_progress` | `{task_id?: string}` | 查任务表 + 子代理状态 |
| `cancel_task` | `{task_id?: string}` | 中断对应任务 |
| `append_requirement` | `{task_id: string, extra: string}` | 追加要求 |

**外加一个反向回调**（DSH → 蝶梦）：

| 函数 | 方向 | 作用 |
|---|---|---|
| `notify_voice_agent` | DSH → 语音 | 干完主动汇报，触发语音开口 |
