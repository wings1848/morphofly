# 真机 e2e 发现的更严重问题（比原 Bug 1 更糟）

## 现象

用例 path-02，用户说：「在 aimeng 项目里跑一下测试」

语音模型实际发出的工具调用：
```json
{"task": "cd /home/wings/Code_Project/M1 && ./run_tests"}
```

**它凭空捏造了一个路径 `/home/wings/Code_Project/M1`。**

`M1` 既不是 `aimeng`，也不是任何已知项目，完全是模型编的。

## 为什么我的修复失效

我的 `extract_unknown_project` 是在**任务文本里找「XX项目」模式**。
但模型把项目名**吞掉了**，任务里根本没有「项目」二字，只剩一个编造的路径。

**所以拦不住是对的 —— 我拦错了地方。**

## 这暴露了真正的问题

提示词规则 1 说：
> 路径和项目名不确定时，必须先追问，绝对不要自己猜或补全。

规则 5 说：
> 「已知项目」表：说「蝶梦」或「morphofly」= /home/wings/Code_Project/morphofly；
> 其余项目名一律追问用户要路径。

**模型两条都没遵守。** 它不但没追问，还编了个路径。

## 根因

1. **提示词约束不可靠** —— 这是第三次验证了（前两次：回复长度、假项目名）
2. **`delegate_task` 的 `dir` 参数是可选的** —— 模型不传时用默认目录，
   但模型选择了「猜一个路径塞进 task 文本里」，绕过了 dir 检查
3. **没有对 task 文本里的路径做校验** —— 我只检查了 `dir` 参数，没检查 task 内容

## 修法（三层防御）

### 第 1 层：校验 task 文本里的绝对路径
从 task 里提取所有 `/xxx/yyy` 形式的路径，
检查每个路径是否存在。不存在就追问。

### 第 2 层：校验 dir
现有逻辑（已做）。

### 第 3 层：强化提示词
明确禁止「把路径写进 task 文本」——
路径只能用 `dir` 参数传。

## 但更根本的问题

**为什么模型会编路径？** 
可能原因：ASR 把「aimeng」识别成了别的东西，
模型听到一个不认识的词，就「合理推测」了一个路径。

**这说明当前提示词的「不猜」约束强度不够。**
需要在提示词里加更明确的负面示例。

## 教训

**修 bug 前必须看真实数据，不能凭想象。**
我以为是「任务里提到了假项目名」，实际是「模型编造了路径」。
如果不看真实工具调用参数，我的修复会一直「单测通过但真机无效」。
