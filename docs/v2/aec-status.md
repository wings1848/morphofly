## 我之前的错误判断（已纠正）

我在 17:50 写过「AEC 只有 1.9dB，方案不行」——**这个结论是错的。**

**真正原因：测试信号太规则。**

AEC3 的延迟估计器遇到**完全周期性的参考信号**会锁到错误的 lag
（稳定正弦在多个延迟上相关性一样高）。
把参考信号改成「基频随时间滑动的谐波」（模拟真实语音语调）后：

| 测试信号 | 回声抑制 |
|---|---|
| 固定频点正弦叠加 | 1.9 dB ❌ |
| **基频滑动的谐波** | **34.5–34.8 dB** ✅ |

**真实 TTS 都是连续语调变化的语音，不会退化成固定正弦。**
所以这个指标在真机上应该没问题。

顺带否掉另外两个猜测：
- `TransparentModeType::Hmm` 没用 —— 问题跟 transparent mode 无关
- 白噪声作参考能到 47dB —— 说明 sonora 本身正常

**教训：测试信号不真实时，测出来的数字毫无意义。**
我差点因为一个假信号否掉一个正确方案。

## sonora API 与预期不同的 4 点

1. `build()` 不返回 `Result` —— 没有构造失败分支
2. 只吃 10ms 块（`num_frames() = rate/100`）—— 所以 320 样本拆 2 个 160 子帧
3. `set_stream_delay_ms` 一旦调用就**关闭自适应延迟估计** —— 默认不调用
4. `Config` 默认全关 —— AEC 必须显式 `Some(EchoCanceller::default())`

## 接入设计（零额外延迟）

- **放在采集分帧之后**：整帧 320 = 2×160，块对齐精确
- **先 tee 再 push**：AEC3 假设 render 块先到，反了参考信号永远晚一拍
- **进程级共享** `aec::shared()`（OnceLock），播放/采集拿同一个实例
- **三档开关**：环境变量 / 构造配置 / 运行中替换，默认开

## 测试覆盖（19 个）

- 静音：输出 < -80dBFS，且静音训练后遇到人声不杀
- 回声抑制：20ms 延迟 34.7dB；另测 10/30/60/100ms 四档全 >20dB
- 双讲：5 个 seed，人声保留 43–55%（要求 >30%）
- 接入不变量：帧长恒 320、i16/f32 一致、24k/48k 重采样、跨线程并发
