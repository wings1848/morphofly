# V2 开发过程中的教训（2026-10-24）

## 1. 测试信号不真实时，数字毫无意义

**我差点否掉一个正确方案。**

我测 AEC 得出「只有 1.9dB，方案不行」，准备换方案。
实际是测试信号用了固定频点正弦 —— AEC3 的延迟估计器遇到
完全周期性信号会锁到错误的 lag。

换成基频滑动的谐波（模拟真实语音）后：**1.9dB → 34.5dB**。

**教训**：测试输入必须接近真实分布，否则测的是「你的测试」，不是产品。

## 2. 测试通过 ≠ 功能正确

**我被自己写的测试骗了一次。**

我说「codex 实测可用」，其实是假的：
- `run_with_command` 里 spawn 用的是 `&self.command`（固定 dsh）
- 但测试**复用了 dsh 的空闲进程池**
- 池里的 dsh 进程拿来跑 codex 任务，当然跑通了

是 clippy 的 `unused variable: command` 警告救了我。

**教训**：当测试路径走了缓存/复用/短路时，bug 会被完全掩盖。
留意「参数没用上」这类警告 —— 它们往往指向真 bug。

## 3. 提示词加规则会互相干扰

修「模型编造结果」花了三轮：

| 轮次 | 改动 | 结果 |
|---|---|---|
| 1 | 加「你绝对不知道任何具体结果」 | 说「好，查着呢」但**不调工具** |
| 2 | 加「必须真的调 delegate_task」 | **回归**，又开始编目录 |
| 3 | 两条合并 + 强调「只回话=假装干活」 | 稳定 ✅ |

**教训**：一次加一条，逐条真机验证。
多条规则同时加，你分不清是哪条起的作用。

## 4. 修 bug 前必须看真实数据

我以为「假项目名」的问题是「任务里提到了不存在的项目名」，
于是写了从任务文本提取项目名的逻辑。

真机一看实际工具调用参数：
```json
{"task": "cd /home/wings/Code_Project/M1 && ./run_test.sh"}
```
**模型压根没提项目名，它凭空捏造了一个路径。**

我的修复方向完全错了。如果不看真实数据，会一直「单测通过但真机无效」。

## 5. 自己写的简单代码也会踩坑

修「假项目名」时踩了两个自己挖的坑：

```rust
// 坑 1：take_while 第一个字符是空格就返回空串
let before = &task[..pos];              // "在 aimeng "（带尾空格）
chars().rev().take_while(is_alnum)      // → "" 永远提取失败

// 坑 2：trim_matches 把路径本身剥了
trim_matches(|c| matches!(c, '.' | '/'))  // "./run_tests" → "/run_tests"
```

**教训**：字符串处理要写测试，别信直觉。

## 6. 环境限制要尽早查清楚

**我在 wings-pc 上花了很多时间测 AEC，最后发现它没有麦克风。**

声卡只有 PCH（主板，纯输出）和 NVidia（HDMI，纯输出）。
播放测试音+录音，比值 1.44 —— 录到的全是底噪。

又试了 snd_aloop 虚拟回环，也不行（数字域回环没有真实卷积关系，
源/录相关性 ≈ 0）。

**教训**：动手前先确认硬件条件。`arecord -l` 一条命令的事。

## 7. 进程误报（技术细节但踩了很久）

```bash
pgrep -f "Code_Project/diemeng"    # 匹配到 SSH 命令自己！
```
造成「14 小时僵尸进程」的误报，白折腾了很久。

**教训**：`pgrep -f` 会匹配命令行字符串，包括你自己。

## 8. 我自己判断错的地方（如实记录）

| 我说过 | 实际 |
|---|---|
| 「AEC 只有 1.9dB，方案不行」 | 测试信号问题，实际 34.5dB |
| 「codex 实测可用」 | 复用了 dsh 进程池的假象 |
| 「谐音误唤醒是产品 bug」 | KWS 层干净，是 e2e 绕过了 KWS |
| 「wings-pc 桌面已就绪」 | 那是登录器的进程，没登录 |
| 「缺陷 #4 需要 300-400 行重构」 | 简化版 50 行就省了 2.6 秒 |

**教训**：说「完成了」之前，先问「我怎么知道这是真的」。

## 9. 改了代码、编了新二进制 —— 却还在跑旧的

修「麦克风打不开」时，我在 gpd 上编了带 PulseAudio 后端的 release 二进制（7 分钟），
重启服务，日志还是 `No such entity`。

查了半天 cpal 的 host 选择，最后发现：**服务根本没跑我编的那个文件。**

```
ExecStart=/tmp/mf-install/usr/bin/morphofly-app   ← 从 deb 解出来的旧版
target/release/morphofly-app                      ← 我刚编的，没人用
```

旧二进制里连 `音频后端：PulseAudio` 这个字符串都没有（`grep -c` = 0）。

**教训**：验证「改动生效」的第一步是**确认跑的是哪个文件**：
`ls -la /proc/$(pgrep -x 程序名)/exe`。这一步 10 秒，能省几小时。

## 10. 兜底机制本身会变成 bug 源

「模型假装干活」的兜底纠正，把一句话变成了 4 个任务。

两条判据错得都不明显：
- **统计单位错了**：按「一次模型响应」清零，但一个用户请求跨多个 response
  （调工具 → 工具结果回灌 → 最终答复），最终答复那一步「没调工具」是**正常的**；
- **事件用错了**：`TranscriptDelta` 名字像「转写」，实际是
  `response.audio_transcript.delta` —— 模型自己说的话。用户的话在解析层就被丢了。

结果：每轮最终答复都触发「你没干活」→ 再派一次 → 循环。
9 秒派了 4 个任务、起了 4 个 DSH 会话、报了 4 遍。

**教训**：
1. 兜底/重试逻辑要有**幂等判据**，不能只看「这一瞬间有没有动作」；
2. 事件名对不上先去看协议原文和解析层，别按名字猜语义；
3. 兜底逻辑的失败模式比它想修的问题更贵 —— 它会把一次变成四次。
