# 打断（barge-in）：验收状态与实现要点

**2026-10-25** ｜ 首次真机验证 + 修掉两个 bug；自动化复现有已知限制

## 结论

- **机制是通的**，真机实测抓到过一次完整打断：
  ```
  20:48:10.078  本地判定开口
  20:48:10.254  ⚡ 本地 VAD 打断（已通知云端停止生成） queued=9952
  20:48:10.358  推状态给前端 state="S2" prev=S4
  SessionStats { interruptions: 1 }
  ```
  （打断后本地反应 **<10ms**：VAD 判定与停播日志落在同一帧里。）
- 自动化复现**不稳定**，原因见「已知限制」；当前建议：结构用 `tools/verify_bargein.sh` 跑，
  最终手感用真人 + 真麦克风确认。

## 设计（本地先停，服务端后确认）

| 路径 | 触发 | 行为 |
|---|---|---|
| 本地 VAD | `LocalVad::push()` 判定有人声 | 停播 + `response.cancel` + 记一次打断 + 通知状态机 S2 |
| 云端事件 | `input_audio_buffer.speech_started` | 停播 + `response.cancel` + 记一次打断 |

两条路径会**同时**看见同一次开口，所以计数做了 2 秒去重（`count_interruption`），
日志也会区分「记一次打断」和「同一次开口的重复信号（不重复计数）」。

判定条件从「播放队列里还有音频（queued>0）」扩展为 **`queued>0 || 状态机在 S3/S4`**：
音频边播边收，队列经常刚好为 0，旧判据会漏掉「回复进行中又来一句」的情况，
然后硬发 `create_response` 被服务端拒（日志里出现过 `ongoing response already exists`）。

## 这轮修掉的 bug（都是真机打断验收暴露的）

1. **打断路径 panic**：在 async 推流任务里调 `tauri::async_runtime::block_on`
   → `Cannot start a runtime from within a runtime` → 推流任务死掉、麦克风不再工作。
   改成 `spawn`。
2. **journal 里写入 ANSI 颜色码**：`state="S4"` 变成带转义的文本，
   脚本 grep 不到；journald 还会把这类消息存成字节数组，`-o json` 解析也踩坑。
   改成只有终端才上色。
3. **「说完」判定 200ms 太短**：一句话换气就被切成两段，第二段拿着已提交的缓冲
   去 `create_response`，服务端回 `ongoing response already exists`。
   改成 400ms。开新轮前如果上一轮还没结束，先取消一次（不重复计数）。

## 已知限制（自动化为什么不稳）

- 测试台用虚拟音源注入，`paplay → null-sink → monitor → 采集` 有 **1–2 秒**延迟
  （高负载更糟），而模型对「请从一数到一百」的回答往往只有 2–4 秒：
  等注入语音真的被采到，模型可能已经说完，队列也空了 → 不构成「回复进行中」。
- 真实场景没有这段延迟（麦克风直接进采集），所以自动化不稳不代表产品不行。
- AEC 在这套测试台上没被验证（App 输出不进采集，见 `audio-topology.md`）。

## 怎么跑

```bash
tools/verify_bargein.sh --dry-run   # 看计划
tools/verify_bargein.sh             # 真机跑一次（大约 1–2 分钟；不花钱，只连一次 StepFun 会话）
```

脚本判定：① 有打断日志 ② 打断后回到 S2 ③ 本地反应（VAD 判定→停播）< 300ms。
“注入→判定”的耗时只报告、不判定（那是测试台延迟）。

## 人工验收（推荐，也最省事）

接上耳机/音箱（有真实输出），喊「小蝶」，让它做一件要念一会儿的事，
说到一半直接说「停」——它应该立刻闭嘴并回到聆听态。日志里会出现
`⚡ 打断：停播 + 取消当前回复（记一次打断）`。
