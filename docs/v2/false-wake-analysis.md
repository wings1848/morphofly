# 谐音误唤醒分析（2026-10-24）

## 现象

真机 e2e 里 4 条负例全部误触发：
- wake-03「小蝶儿真好看」
- wake-04「蝴蝶飞走了」
- wake-05「这个字读小的」
- edge-01 纯静音

## 关键：这不是 KWS 层的问题

**KWS 测试是干净的**：`detect_in_file` 对 8 条负例 0 误唤醒。

原因是 **e2e_drive 直接连云端，不走 KWS**。
而真实产品的链路是：

```
麦克风 → [KWS 本地检测] → 命中才连云端 → 云端 ASR → 模型
                ↓
           不命中就停在这
```

所以真实产品里，「小蝶儿」会被 KWS 的
`num_trailing_blanks >= 4` 要求挡住（关键词后必须连续 4 帧 blank）。

## 那为什么 e2e 会误报

因为我本机**编不了 `--features kws`**（缺 libstdc++，无 root 装不了），
所以 e2e_drive 的 KWS 前置门代码写好了但没生效，
测试实际走的是「直接连云端」。

**云端 ASR 确实会把「小蝶儿」听成「小蝶」** —— 但这在真实产品里
不会导致误唤醒，因为语音根本没送到云端。

## 结论

| 层 | 状态 |
|---|---|
| KWS 本地检测 | ✅ 干净（8 条负例 0 误触发）|
| 云端 ASR 谐音 | ⚠️ 确实会听错，但真实产品不会走到这 |
| 完整链路 | ⏳ **未验证**（需要能编 kws feature 的环境）|

## 要验证需要什么

在有 `libstdc++` 的机器上（wings-pc / wings-gpd 都有）：

```bash
cargo run --features kws --example e2e_drive -- --file <负例音频>
# 期望输出 kws_blocked: true
```

## 我要承认的事

**我之前说「谐音误唤醒是真实产品 bug」是不准确的。**
真实产品有 KWS 前置门，这个问题大概率不存在。
但我不能断言它不存在 —— 因为完整链路没验证过。

正确表述：**KWS 层干净，云端层会听错，二者之间有一道门，门的效果未验证。**
