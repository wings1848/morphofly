# 项目 Review · 体验与交互问题清单

**日期**：2026-10-24
**范围**：MorphoFly V1 全部代码（9765 行）+ 画布新需求
**目的**：找出体验和交互的可优化点，为 V2 开发提供依据

## 一、致命问题（用户明确抱怨或无法使用）

### 1. 窗口无法关闭 / 无法找回 ⚠️ 最严重

**现状**（`app/src-tauri/tauri.conf.json`）：
```json
{
  "transparent": true,
  "decorations": false,      // 无边框 → 没有关闭按钮
  "alwaysOnTop": true,       // 始终置顶 → 遮挡其他窗口
  "skipTaskbar": true        // 任务栏里不显示 → 切走了找不回来
}
```
**没有托盘图标**（`app.trayIcon` 未配置）。

**后果**：用户启动后，球永远浮在最上层、任务栏没有图标、没有关闭按钮。
**只能 `pkill` 才能退出。** 用户说的「启动时不要干扰用户正常使用电脑设备」正是这个。

**修法**（需求里也提到了）：
- 加系统托盘图标（右键菜单：显示/隐藏/退出）
- 球支持拖动 + 自动贴边
- 默认位置避开屏幕中心（比如右下角）

### 2. 外放会自我打断（AEC 缺失）

**现状**：麦克风听到扬声器输出 → 本地 VAD 判定「用户开口」→ 立刻停播。
**后果**：不戴耳机就没法用。
**修法**：见 AEC 方案（subagent 侦察中）。

### 3. 提示词里的项目表过时

当前 `DEFAULT_INSTRUCTIONS` 规则 5：
> 「已知项目」表：说「蝶梦」或「diemeng」= /home/wings/Code_Project/morphofly

**问题**：英文名已经改成 morphofly，但提示词还写 diemeng。
更根本的问题：**硬编码路径表不可扩展**。用户有几个项目就要改一次代码。

**修法**：改成配置文件驱动（`~/.diemeng/projects.toml`），支持语音增删。

## 二、体验问题（能用但难用）

### 4. 回复不够简洁

当前提示词只说「说话简短口语化」，没有量化。
实测回复示例（`runs/*/evidence/b9-multiturn.md`）：
> 「你的项目还在跑呢，估计再过几分钟就好啦。要不要我帮你盯着点？」

**两句话，42 字。** 用户要求「极其简洁」。应该压到一句、20 字内。

**修法**：提示词里给出明确字数和句式约束，`clean_for_speech` 也加长度上限（当前 160 字符）。

### 5. 任务派发没有确认环节

**现状**：语音模型判断意图后直接调 `delegate_task`，没有「要开始了吗？」的确认。
**后果**：ASR 听错时，会直接开始做错的任务。

**修法**：加「意图明确才派 / 复杂任务先确认」的分流（subagent 侦察中）。

### 6. 只有一个 agent，无法切换

**现状**：写死连 DSH（`dsh --profile acp`）。
用户要求「多个 agent（dsh、codex）、语音切换工作目录和模型」。

**修法**：见多 agent 方案（subagent 侦察中）。

### 7. 内存 488MB

Tauri + WebKitGTK 固有开销。用户明确说「太吃内存」。
**修法**：见内存方案（subagent 侦察中）。

## 五、文案问题（"极其简洁"的具体差距）

用户要求「语音消息回复**极其简洁**」。我逐条检查了所有给用户听的文案：

| 位置 | 当前文案 | 问题 | 建议 |
|---|---|---|---|
| `dispatch.rs:121` 派活 | 「好，记下了，**任务号 001**。干完我跟你说。」 | 任务号对用户无意义，23 字 | 「好，干完说」 |
| `dispatch.rs:119` 派活（紧急） | 「好，这就去办，**任务号 001**。」 | 同上 | 「好，马上去」 |
| `dispatch.rs:154` 查进度 | 「现在有 3 个任务：001 是跑着，002 是干完了，003 是失败了。」 | 编号罗列，用户听不懂 | 「三个活：一个在跑，两个完了」 |
| `dispatch.rs:180` 取消 | 「好，**001** 我已经让它停了。」 | 编号 | 「好，停了」 |
| `dispatch.rs:86` 路径确认 | 「（建议目录）我没敢直接开工，你确认一下是哪个目录？」 | 太长且生硬 | 「是某某目录吗？」 |
| `dispatch.rs:248` 路径错误 | 「路径「/xx/yy」不存在。」 | 念路径，违反"不念路径"规则 | 「你说的那个目录没找到」 |
| `clean_for_speech` 上限 | **160 字符** | 160 字读出来要约 30 秒 | **40 字**（约 8 秒） |

**核心问题：文案设计得像 CLI 输出，不像人说话。**

### 改法

1. **去掉所有任务号**（内部用 ID，对用户只说"这个活"）
2. **长度硬限制从 160 降到 40 字**
3. 提示词加明确约束：「回答不超过 20 个字，除非用户追问细节」

## 六、交互流程问题

### 现在的流程
```
用户说话 → 本地 VAD 判说完 → commit → 云端响应
  → 语音模型判断意图 → 直接调 delegate_task → 立刻开工
```

**没有确认环节。** ASR 听错一个字，就直接做错的事。

### 用户要求的流程
> 当用户意图明确要开始进行任务时才派发 work agent，可主动询问用户是否确认进行任务

**建议流程**（分三档）：

| 任务类型 | 判断依据 | 流程 |
|---|---|---|
| 闲聊/问答 | 无动作意图 | 直接回答 |
| 简单任务 | 意图明确、路径已知、单步 | **直接派**，回一句"好，干完说" |
| 复杂任务 | 多步、要规划、路径不确定 | **先问确认**："要我帮你做 X 吗？" |

**关键：不能让确认变成啰嗦。** 简单任务问「要开始吗」会让用户烦。

### 判断在哪一层做

**不能靠语音模型自己判断**（不可靠）。放在 `dispatch.rs`：

```rust
// 伪代码
match classify(&task) {
    Simple if path_known => dispatch_now(),
    Complex | PathUnknown => ask_confirm(),
}
```

`classify` 用规则：任务长度、是否含多动作词、路径是否在已知表里。
