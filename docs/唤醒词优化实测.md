# 唤醒词优化 · 实测报告

> 日期：2026-10-23
> 环境：wings-tx-us1，sherpa-onnx 1.13.8，模型 `sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20`（int8）
> 测试集：`test-audio/` 的 15 个音频 + 1 个拼接样本
> **本报告所有数字都是本机真跑出来的，不是查资料抄的。**

---

## 0. 一句话结论

**`num_trailing_blanks` 从 1 改成 4，误唤醒从 1/8 降到 0/8，召回不变（8/8），延迟零代价。**

这是一个之前完全没被发现的参数。调它，比换词、换引擎、加二级验证都划算。

---

## 1. 问题复现

### 基线（默认参数）

| 配置 | 召回 | 误唤醒 | 谁误触发了 |
|---|---|---|---|
| `num_trailing_blanks=1`（默认） | 8/8 | **1/8** | `13_fp_xiaodieer`（「小蝶儿真可爱」） |

**「小蝶儿」被识别成了「小蝶」。** 这不是偶然——见第 2 节。

### 为什么阈值救不了（实测）

扫描 `keywords_threshold` 从 0.05 到 0.50：

| threshold | 召回 | 误唤醒 |
|---|---|---|
| 0.05 | 7/7 | 1/7 |
| 0.15 | 7/7 | 1/7 |
| 0.25 | 7/7 | 1/7 |
| 0.35 | 7/7 | 1/7 |
| 0.50 | 7/7 | 1/7 |

**八档阈值，误唤醒纹丝不动。** 这证实了之前的调研结论：调阈值是白费力气。

---

## 2. 根因：机制层面发生了什么

### 2.1 阈值管不了「小蝶儿」

sherpa-onnx 源码 `transducer-keyword-decoder.cc` 的触发条件：

```cpp
if (best_hyp.num_trailing_blanks > num_trailing_blanks_ &&
    ys_prob >= matched_state->ac_threshold) { /* 触发 */ }
```

- `ys_prob` 是匹配 token 的**平均声学概率**
- 「小蝶儿」的前两个音节 `x iǎo d ié` 与「小蝶」**声学上高度相似**
- 所以它的声学概率本来就高，阈值压不住

### 2.2 实测确认：模型分不开「小蝶」和「小蝶儿」

我把「小蝶儿」也注册成关键词，看它能不能匹配到正确的词：

```bash
printf 'x iǎo d ié @小蝶\nx iǎo d ié r @小蝶儿\n' > kw_multi.txt
```

**结果**：「小蝶儿」音频仍然命中 **`小蝶`**，不是 `小蝶儿`。

**这说明模型在声学层面就把两者合并了。** 加关键词没用。

### 2.3 真正的开关是 `num_trailing_blanks`

这个参数的含义：**关键词之后，必须连续出现 N 帧 blank（静音/非语音），才真正触发唤醒。**

为什么它能治「小蝶儿」：
- 「小蝶」说完 → 后面没有内容 → 连续 blank 帧 → **正常触发**
- 「小蝶儿」→ 「儿」紧接着产生新 token → **blank 连不起来** → 被抑制

**这是一个天然的近音词过滤器，而且不需要额外计算。**

## 3. 实测结果

### 3.1 参数扫描（核心发现）

| `num_trailing_blanks` | 召回 | 误唤醒 | 误触文件 |
|---|---|---|---|
| 1（默认） | 7/7 | **1/7** | `13_fp_xiaodieer` |
| 2 | 7/7 | 1/7 | `13_fp_xiaodieer` |
| 3 | 7/7 | 1/7 | `13_fp_xiaodieer` |
| **4** | **7/7** | **0/7** | **无** ✅ |
| **5** | **7/7** | **0/7** | **无** ✅ |
| 6 | 6/7 | 0/7 | 漏检 1 个 |
| 8 | 6/7 | 0/7 | 漏检 1 个 |

**拐点在 4。** 1–3 都压不住「小蝶儿」，4 开始干净。

### 3.2 稳定性验证（nb=4）

**换阈值**（nb 固定 4）：

| threshold | 召回 | 误唤醒 |
|---|---|---|
| 0.15 | 7/7 | 0/7 |
| 0.20 | 7/7 | 0/7 |
| 0.25 | 7/7 | 0/7 |
| 0.30 | 7/7 | 0/7 |
| 0.35 | 7/7 | 0/7 |
| 0.40 | 7/7 | 0/7 |

**全区间干净。** 说明 nb=4 不依赖阈值调参。

**换 score**（nb 固定 4）：

| score | 召回 | 误唤醒 |
|---|---|---|
| 0.5 | 7/7 | 0/7 |
| 1.0 | 7/7 | 0/7 |
| 1.5 | 7/7 | **1/7** |
| 2.0 | 7/7 | **1/7** |

**score 调高会破坏效果。** 保持默认 1.0。

### 3.3 延迟代价：**零**

| nb | 01_wake | 02_slow | 06_cmd |
|---|---|---|---|
| 1 | 1.12s | 1.12s | 1.12s |
| **4** | **1.12s** | **1.12s** | **1.12s** |
| 5 | 1.12s | 1.44s | 1.12s |

**nb=4 与 nb=1 的检测时间完全一样。**

**为什么**：edge-tts 生成的音频在「小蝶」后有 1.15s 尾部静音，
4 帧 blank 只需要 160ms，绰绰有余。**多等的那点时间被已有的静音吃掉了。**

### 3.4 关键风险验证：连续说话会不会漏检？

**担心**：真实说话是「小蝶，帮我看看项目进度」，中间没有静音。nb=4 会不会等不到 blank 就漏掉？

**做法**：裁掉「小蝶」的尾部静音，直接拼上指令音频，构造无间隔样本 `ZZ_joined.wav`（3.44s）。

| nb | 结果 |
|---|---|
| 1–8 | ✅ 全部唤醒 |
| 10 | ✅ 唤醒 |
| 12 | ❌ 漏检 |
| 15 | ❌ 漏检 |

**nb=4 在连续语音下完全正常。** 安全区间是 **4–10**，12 开始漏检。

**原因**：模型在「小蝶」和后续音节之间仍会产出少量 blank 帧，4 帧够用，12 帧就等不到了。

## 5. 被否决的方案（附实测理由）

### 5.1 声纹验证 —— 实测失败

**想法**：只认主人的声音，别人说「小蝶」不唤醒。

**实测**（`3dspeaker_speech_campplus_sv_zh-cn_16k-common.onnx`，27MB）：

以「小蝶」为参考，算其他音频的余弦相似度：

| 音频 | 相似度 |
|---|---|
| 01_wake_short（同一个人说小蝶） | 1.0000 |
| 02_wake_slow | 0.9188 |
| **13_fp_xiaodieer（小蝶儿）** | **0.8392** |
| 15_neg_xiaode（小的） | 0.7590 |
| 06_cmd_progress | 0.7351 |
| 03_wake_fast_long | 0.6092 |
| 11_neg_chat | 0.3183 |

**「小蝶儿」的相似度（0.84）比「小蝶小蝶」（0.61）还高。**

**结论**：声纹识别的是**谁在说**，不是**说了什么**。
同一个人说「小蝶儿」，声纹相似度天然就高。**这个方案治不了近音词。**

### 5.2 两级 ASR 验证 —— 不建议

**想法**：KWS 触发后用 ASR 转写确认，看是不是真的「小蝶」。

**问题**：
1. **ASR 很可能把「小蝶儿」规范化成「小蝶」**——那就等于没验证
2. 代价大：SenseVoice int8 要 **228MB**，RTF 0.099–0.436
3. 延迟 +几百 ms，破坏唤醒体验

**替代**：子代理建议用轻量中文模型 `zh-14M`（25MB，RTF 0.028–0.038），但**未实测**。

**既然 nb=4 已经零成本解决问题，没必要上两级验证。**

### 5.3 负关键词抑制 —— 源码确认不支持

子代理读了 `context-graph.cc`：`ContextGraph::Build()` 只接收 token_ids / scores / phrases / ac_thresholds，**没有减分通道**。`KeywordSpotterConfig` 也没有 negative/suppress 字段。

**网上如果有人说能配负关键词，那是错的。**

## 6. 推荐配置

```python
sherpa_onnx.KeywordSpotter(
    tokens=...,
    encoder=...,
    decoder=...,
    joiner=...,
    keywords_file="keywords.txt",
    num_threads=1,
    keywords_score=1.0,          # 保持默认，调高会破坏效果
    keywords_threshold=0.25,     # 保持默认，实测不敏感
    num_trailing_blanks=4,       # ★ 关键：从默认 1 改成 4
)
```

**再加两条工程措施**（成本为零）：

1. **唤醒后 800ms 冷却**——防止连续误触发
2. **提供关闭语音唤醒的开关**——误触发烦人时的兜底

## 7. 边界与风险

| 项 | 说明 |
|---|---|
| **安全区间** | nb 在 **4–10** 之间都安全，≥12 会漏检连续语音 |
| **推荐值** | **4**（最小有效值，留足余量） |
| **测试集规模** | 只有 8 正 + 8 负，**样本偏小**，需在真实环境补测 |
| **测试音频来源** | 全部是 edge-tts 合成，**不是真人录音**，真实场景需复验 |
| **未测** | 真人说话、嘈杂环境、远场、多人同时说话 |
| **未测** | ESP32 上的 esp-sr 是否有同类参数（**待查**） |

**最重要的一条**：这 8+8 的测试集只是**方向性验证**，
证明「nb=4 有效」这个方向对，但**具体数字不能当最终指标**。
