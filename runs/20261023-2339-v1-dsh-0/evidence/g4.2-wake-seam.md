# 阶段 4 · 唤醒接缝（KWS → 状态机 → 云端 → 聆听）

## 两段证据

### 1. KWS 识别能力（Python 侧，真机）
见 `g4.1-kws-recall.md`：**召回 9/9，误唤醒 0/8**（含「小蝶儿」「蝴蝶」「小的」谐音陷阱）。

### 2. 状态机接缝（Rust 侧，真机）
```bash
tools/pcrun.sh 'cargo run -q -p diemeng-core --example wake_word -- \
  --file testdata/audio/01_wake_short.mp3 --seconds 6'
```

```
[wake_word] 上行来源：文件 testdata/audio/01_wake_short.mp3（代替麦克风）
[wake_word] 待机监听中
[wake_word] 🔊 检测到唤醒（视觉强度 0.69）→ S1
[wake_word] → S2 聆听中…
[wake_word] 💤 静音超时 → S0
```

**完整循环 S0 → S1 → S2 → S0 走通**，且没人说话时保持 S0（另一次 8 秒真麦克风空跑：
`累计迁移 0 次，最终状态 S0` —— 零误触发）。

## 诚实说明：这是骨架不是完整实现

| 项 | 现状 |
|---|---|
| KWS 识别率 | ✅ Python 侧已实测（9/9 召回、0/8 误唤醒） |
| Rust 侧常驻 KWS | ❌ 未接入。需要给 core 加 `sherpa-onnx` crate（现在只有 Python 侧验证） |
| 当前 example 的「唤醒检测」 | 能量门限占位（视觉强度 > 0.55 连续 3 帧），**不是真的 KWS** |
| 接缝结构 | ✅ 已固定：检测器 → `Stimulus::WakeWord` → 状态机 → `Stimulus::Connected` → S2 |

**为什么先这么做**：把接缝先钉死，等 sherpa-onnx Rust 绑定接进来时，只换中间那个检测器，
状态机、云端连接、UI 全部不用改。
