## ⚠️ 必须诚实标注：这个 22ms 不能直接当成「用户感知延迟」

原因：**StepFun 是全双工「边想边说」模型**。
它在用户还在说话时就已经开始生成回复，等 `speech_stopped` 事件到达时，音频基本已经准备好了。
所以「speech_stopped → 第一个 delta」只有 22ms，**这是模型架构的红利，不是我们优化出来的**。

真正决定用户感知的还有两个环节没算进来：

| 环节 | 量级 | 状态 |
|---|---|---|
| 用户物理停止说话 → 服务端 VAD 判定说完（`silence_duration_ms=450`） | **≈450ms** | 已配置，未单独测 |
| 收到音频 → 攒够抗抖动余量 → 真正出声 | **200–500ms** | 播放器参数，可调 |
| 合计（估算） | **≈670–970ms** | **落在 P1 合格线附近，不达理想值** |

**结论：P1 判「有条件通过」。**
22ms 这个数字是真的，但它是链路中间一环的延迟；
要在真人对话里量「说完 → 听到声」，需要：真人对着麦克风说完一句话、用外部录音量到扬声器出声的时间差。
这一步没做，标记为未验证。
