## 踩坑（都是实测踩出来的，已写进代码注释）

| 坑 | 现象 | 解法 |
|---|---|---|
| **`energy_awakeness_threshold` 默认 2500 太高** | 正常音量 TTS 音频推流，VAD **完全不触发**，等 45s 没有任何 response | 调到 **500** 才出全链路 |
| `turn_detection.type` 只支持 `server_vad` | 传 `"none"` → `error: only server_vad is supported (400)` | 不支持手动模式 |
| 开着 server_vad 时手动 commit | `error: commit when server vad` | 轮次必须由服务端 VAD 驱动，客户端不 commit |
| `voice` 传非法值 | `error: voice default is not valid`，会话不断 | 用 `jingdiannvsheng` |
| 纯静音 + `response.create` | `error: continue_final_message is set but the final message does not exist` | 必须先有真实人声进 buffer |

以上全部写进 `core/src/realtime/protocol.rs` 的 `TurnDetection::default()` 注释里，避免后人再踩。

## 影响

- 端到端延迟目标 **800ms 已达标**，甚至打到了理想值 500ms 以内。
- StepFun 的会话是 **服务端 VAD 驱动**的，这正好符合「全双工、可打断」的架构；
  客户端只需要持续推流 + 收到 `SpeechStarted` 时本地停播（barge-in）。
