# 打断（barge-in）分析：架构与 StepFun 的 VAD 延迟冲突

**日期**：2026-10-24 05:30 (+08:00)
**结论：打断无法在 StepFun 上做到 <300ms。这是架构级冲突，不是实现问题。**

## 实测

```
[bargein] 阶段 1：推 testdata/audio/06_cmd_progress.mp3 让模型开口
[bargein] 模型正在说话，队列 0 帧 —— 现在推打断音频
[bargein] 播放帧数: 101760
[bargein] ⚠️ 没打断成功（云端没有报 speech_started）
```

## 为什么打不断

我们的设计（docs/开发方案.md §4.1）是：

```
本地 VAD 检测到人声 → 立刻清播放队列 → 再推流给云端确认
```

**但「本地 VAD」这一块我们还没实现。** 现在代码里只有一个触发点：
`RealtimeEvent::SpeechStarted`，而这个事件来自**云端**。

云端的 `speech_started` 什么时候来？
`evidence/p1-vad-parameter-sweep.md` 已经量过：
**服务端 VAD 判定「用户开口」+「说完」整套要 1.6 秒级**。

而模型说完一句话通常只要 1–3 秒。
所以等云端报 `speech_started` 时，模型很可能已经说完了 —— 实测就是「队列 0 帧」。

## 这是「本地先停」设计的真正理由

原设计写得很清楚：

> 等云端事件走完一圈要 200–400ms，用户会觉得「它不听我」。

现在实测发现实际不是 200–400ms，而是 **1.6 秒**。
所以「必须在本地做 VAD」不是优化项，**是打断功能能否存在的先决条件**。

## 要做完打断需要什么

1. **本地 VAD**：用 silero-vad（或简单的能量门限 + 过零率）在采集侧实时判断「有人开口」
   - CPU 开销小，可跑在音频线程里
   - 判定延迟可以做到 50–100ms
2. **触发链**：本地 VAD 命中 → **立刻** `player.stop_now()` → 再推音频给云端
3. **跟服务端的协调**：本地先停，云端 `speech_started` 只作为「确认」而非「触发」

## 现在代码里已经有的部分

- `AudioPlayer::stop_now()` 实测 **773 纳秒**清空队列（I4）—— 停播本身极快
- `VoiceSession::run()` 里有 `SpeechStarted → stop_now()` 的接线
- 缺的只有「本地 VAD 检测器」这一个组件

## 我对验收标准 P2 的判断

**P2 要求「打断延迟 <300ms」，在 StepFun 上无法通过云端事件达成。**
必须补本地 VAD。这是一个明确的、有边界的待办，不是「再调调参数」。

## 建议

1. 加 silero-vad（或复用 sherpa-onnx 自带的 VAD：`sherpa_onnx::Vad`）
2. 本地 VAD 命中 → `stop_now()` + 状态机回 S2
3. 重测 P2

**这是一天以内能做完的工作**，不依赖用户决策。
