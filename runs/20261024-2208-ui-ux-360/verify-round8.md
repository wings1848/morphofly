# 第 8 轮验证：稳定性测试（连跑 3 次）

**日期**：2026-10-25 01:26
**目的**：单次成功不算「可用」。连跑 3 次看真实成功率。

## 结果：0/3 —— 但抓到了真因

```
第 1 次  派活=1（本地代派=0） DSH会话=0 汇报=1 出错=1  ✗
第 2 次  派活=1（本地代派=0） DSH会话=0 汇报=1 出错=1  ✗
第 3 次  派活=1（本地代派=1） DSH会话=0 汇报=1 出错=1  ✗
```

三次都派活了、都汇报了（说明链路通），但 DSH 会话全失败。

## 真因（靠上一轮加的错误链才看得到）

```
report=失败了：出错了：建 DSH 会话失败: 建 DSH 会话超时（20s）
```

手工复现（`/tmp/dsh_probe.py`，直连 dsh --profile acp）：

```
initialize:   15.29s  ok=True     ← 有时候要这么久
session/new:   1.49s  ok=True
```

`initialize()` 原来的写法是「最多等 2 秒，没等到就往下走」：
1. 服务端还没握手完，我们就发了 `session/new`
2. `session/new` 迟迟不回 → 20 秒超时
3. 用户听到「失败了：建 DSH 会话失败」

至于 initialize 为什么有时 15 秒：大概率在启 MCP 服务
（本机 acp profile 里配了 SSH 桥的 computer-use MCP）。

## 修法（commit `d28b5a3`）

- `initialize()`：真等到结果，最多 30 秒；等不到就明确报「DSH 握手超时」
- `session/new`：超时 20s → 50s

## 这轮的方法论收获

**先做稳定性测试再谈优化。** 前面几轮都在「单次能过」上做判断，
换个时段连跑三次就发现是 0/3 —— 而这只有连环测试才看得出来。
