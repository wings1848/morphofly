## 最重要的 5 条教训

### 1. 测试通过 ≠ 功能正确
`set_context(agent)` 我先宣布「codex 实测可用」，实际 spawn 用的是
`&self.command` 而非传入的 `command`，测试复用了 dsh 的空闲进程池掩盖了 bug。
**是 clippy 的 unused variable 警告救的。**

→ 改进：**参数没用上的警告必须查，往往指向真 bug。**

### 2. 测试信号不真实时，数字毫无意义
AEC 我测出 1.9dB 就判断「方案不行」，实际是测试用了固定正弦，
AEC3 的延迟估计器锁错 lag。换基频滑动信号 → 34.5dB。
**差点否掉一个正确方案。**

→ 改进：**测试输入必须接近真实分布。**

### 3. 测试绕过组件时，测出的问题可能不存在
我说「谐音误唤醒是产品 bug」，实际 e2e 绕过了 KWS 直接连云端。
KWS 实测对 3 条谐音全 0 命中。方向判断完全反了。

→ 改进：**测试失败先问「这个测试走的是真实路径吗」。**

### 4. 提示词加规则会互相干扰
修「编造结果」花了 3 轮：
- 加「不知道自己不知道」→ 光说不做
- 加「必须调工具」→ 又变回编造
- 两条合并 + 强调「只回话=假装干活」→ 稳定

→ 改进：**一次加一条，逐条真机验证。关键行为要有代码兜底。**

### 5. 「切换类」功能的通病：改本地副本不通知外部
- cancel_task：只改 TaskStatus，没停 DSH
- set_context(model)：只改 ctx.model，没调 API
- set_context(agent)：只改字段，spawn 用固定命令

→ 改进：**每个切换类功能必须有端到端测试，不能只测本地状态变了。**

## 流程改进（要改哪个文件）

1. **`~/.agents/AGENTS.md`**：在「六个闸门」下加一条：
   > **假功能检测**：任何「切换类」功能（agent/模型/目录/设置），
   > 必须有一条端到端测试验证「外部系统真的收到了变更」，
   > 只测本地字段变化不算通过。

2. **`devflow` S5 硬规则**：验收审计时必须抽查「这个功能的副作用真的发生了吗」，
   不只检查「返回值和预期一致吗」。

3. **本项目 `docs/v2/lessons.md`**：已记录 8 条教训，作为后续开发的检查清单。

## 关于 devflow 的诚实评价

**用了 CLI 记录状态和闸门，但没有严格执行「每阶段先落产物再进下一阶段」。**

具体表现：
- S1/S2 的 spec/acceptance 当时写了，facts/adr/plan/tasks **是事后补的**
- S3 验红没留 `evidence/red.log`
- S5 独立评审是 subagent 做的侦察，不是按验收表逐条判

**原因**：一开始把 devflow 当「记录工具」而不是「强制流程」，
先进了实现，回头补文档。

**下次应该**：S1/S2 产物没落盘就不允许写代码。
