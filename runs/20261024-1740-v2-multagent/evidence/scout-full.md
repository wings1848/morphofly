也没有 sudo —— webrtc-audio-processing 在本机**编不出来**。sonora 17 秒编完。

### 实测数据（subagent 合成信号测试，用项目自己的判据）

| 回声增益 | 无 AEC 残余 | 自我打断 | 有 AEC 残余 | 衰减 |
|---|---|---|---|---|
| 0.10 | 0.0103 | 安全 | 0.0004 | 28.4 dB |
| **0.20** | **0.0206** | **开始误触发** | 0.0008 | 28.3 dB |
| 0.35（正常外放） | 0.0361 | 误触发 | 0.0012 | 29.6 dB |
| 0.90（很响） | 0.0928 | 误触发 | 0.0026 | 31.0 dB |

**关键**：项目 `voice.rs` 的 `VOICE_RMS = 0.02` 门限，
只要回声超过 0.02 就必然自我打断。加 AEC 后残余稳定 <0.003，留 6 倍余量。

### 会不会牺牲打断能力？（最重要的一张表）

| 方案 | 回声误触发 | 真打断检出 |
|---|---|---|
| 现状（无 AEC） | 4 次 | 1 次 ✅ |
| **加 AEC3** | **0 次** | **1 次 ✅** |
| 播放时全静音 VAD（半双工） | 0 次 | **0 次 ❌** |

**AEC 不牺牲打断，半双工方案会。** 所以「播放时暂停 VAD」这条捷径必须排除。

### 集成：不改音频架构

只插一个点：
```
cpal → 下混 → 重采样 → 320样本帧
                          │

   reference ──►│  AecProcessor      │ ← 唯一新增
   (append_pcm16 │  sonora AEC3       │

                          │
```

`capture.rs`（~20 行）、`playback.rs` 的 `append_pcm16` tee（~10 行）。

⚠️ sonora 要求 rustc ≥ 1.91（本机 1.99 ✅ / wings-pc 1.98 ✅ / CI stable ✅），
但 workspace `rust-version = "1.82"` 要改。

### 关键判断

**① DSH 插件是唯一「两天多一个端」的选项**
现成接缝齐全：`acp.rs`（完整 ACP 客户端）、`bridge.rs`、`examples/voice_task.rs`（实测 3.6s）。
`core` 已不依赖 Tauri。只需加 `core/src/bin/morphofly-voice.rs`（~50 行）+ 插件包。

**② Web 端不能复用 Rust core（推翻我之前的假设）**
`core` 依赖 tokio(net/process)、cpal、rodio、sherpa-onnx、rustls —— **全都编不过 wasm32**。
改 no_std 等于重写。

**但有一条反直觉的好消息**：项目铁律「WebView 不碰麦克风」的原因是「拿不到 AEC 参考信号」。
**独立浏览器页面里播放和采集在同一个 AudioContext，`echoCancellation:true` 的参考信号是完整的**
—— 浏览器 AEC 在 Web 端真能用。

粒子球可 1:1 复用 `app/frontend/src/orb/`（11.4KB 纯 JS，零依赖）。

⚠️ **阻塞点**：Web 端要派活，但现在是 `core` spawn `dsh` 子进程，浏览器做不到。
**DSH 必须有 HTTP/WS 入口——这点未确认。**

**③ ESP32 能保住「小蝶」这个名字（新发现）**
之前文档说 esp-sr 内置 35 个中文词、没有「小蝶」，给了三个选项。
但乐鑫官方文档显示 **esp-sr 支持用 TTS 样本自己训唤醒词**
（每模型最多 5 词，词长 3–6 音节，「小蝶」正好符合）。
项目已在用 edge-tts，技术栈天然契合。**训练周期以周计，V3 前就要开工。**

## 三、内存（最有价值的发现）

### 关键方法论纠正：之前用 RSS 是错的，该用 PSS

RSS 会把共享 .so 重复计算。subagent 用 `/proc/PID/smaps_rollup` 的 PSS 实测：

| 进程 | RSS | **PSS（真实）** |
|---|---|---|
| `morphofly-app` | 260MB | **206MB** |
| `WebKitWebProcess` | 171MB | **125MB** |
| `WebKitNetworkProcess` | 70MB | **39MB** |
| 合计 | 506MB | **371MB** |

主进程 206MB 拆开：
- `RssAnon` **81MB** ← 真正属于我们的堆（tokio/sherpa/rodio/rustls）
- `RssFile` **157MB** ← 映射的 .so（WebKit 24.7 + NVIDIA 27.1 + LLVM 25.7 + …）

**所以之前「488MB 是 WebKit 固有开销」这个说法只对一半。**
真正我们的代码只有 81MB，其余是 .so 映射和 WebKit 子进程。

### 决定性 A/B 实验：粒子动画只占 73MB

| 版本 | 主进程 PSS | WebKitWeb | WebKitNet | 合计 |
|---|---|---|---|---|
| 完整粒子（现状） | 206MB | 125MB | 39MB | **371MB** |
| **空白页（零 JS）** | 162MB | 83MB | 36MB | **283MB** |

**删掉粒子动画只省 88MB，还剩 283MB —— 远超 150MB。**
这一条否掉了「只优化前端」的幻想。

### 最反直觉的发现：wgpu 比 WebKit 更吃内存

| 方案 | 内存 PSS | CPU @60fps |
|---|---|---|
| 现状 Tauri+WebKit | 371MB | 3.7% 空闲 |
| **winit + softbuffer** | **6MB** | **64.6%** @720粒子 |
| **winit + wgpu (Vulkan)** | **137–178MB** | 未测出 |

**「换成 wgpu 就能省内存」是错的。** NVIDIA 驱动（27MB）+ LLVM（25MB）+ EGL 一圈全映射进来。

独立佐证：egui 官方 issue #7761 显示同一份 UI，glow 54MB / wgpu VK 129MB。

### 原生重写粒子的难度

| 元素 | 难度 |
|---|---|
| 粒子位置/演化 | ★☆☆ |
| 加色混合 + 边缘衰减 | ★★☆ |
| 六态参数表 + 平滑 | ★☆☆ |
| **4 层同心径向渐变光晕** | **★★★** |
| **「体积光」边缘衰减** | **★★★** |
| 64 根频谱弧 + 脉冲环 | ★★☆ |

subagent 实际写了 prototype：形态对了，但**明显缺光晕层次**。
且 CPU 64.6% 是朴素实现，要预渲染 sprite 才能降下来（再 2 天）。

### 分阶段路径（推荐）

| 阶段 | 动作 | 工期 | 内存 | 决策点 |
|---|---|---|---|---|
| **0** | 免费优化（见表） | 0.5 天 | 488 → ~400MB | 立刻做 |
| **1** | 原生壳 + 最简粒子 | 3 天 | **40–60MB** | 给用户看视觉能否接受 |
| 2 | 补光晕 + CPU 优化 | 4–6 天 | 40–60MB | 不接受就退回，损失仅 3 天 |

### 免费优化（省 ~90MB，无风险）

| 动作 | 省多少 | 依据 |
|---|---|---|
| **KWS 只在待机时开、进会话关掉** | **~42MB** | 实测 KWS=1 anon 81MB / KWS=0 anon 48MB |
| `WEBKIT_DISABLE_MEMORY_PRESSURE_MONITOR=1` | 未知 | WebKit bug 297648 |
| startup 后 `malloc_trim(0)` | 未知 | glibc arena 不归还 |

KWS 那 42MB 还有产品含义：唤醒词常驻费电，做成「只在 S0 开」既省内存又省电。
